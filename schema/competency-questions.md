# コンピテンシー質問(CQ)台帳

オントロジーは「良さそうなクラスを並べる」のではなく、**KGが答えられるべき
質問を先に文書化し、それに答えられるかで妥当性を判定する**(設計書§5.6)。
CQに答えられないオントロジーは、クラスがどれだけ整っていても不合格とする。

各CQには `queries/cq/` に対応するSPARQLがあり、`tests/test_competency_questions.py`
がテストとして実行する。**CQを追加したらテストも増える。**

| P0-5 | 正準IDに解決できなかった参照はどれだけあるか | `p0-05-unresolved-count.rq` |

P0-3〜P0-5 は「**データの欠けと鮮度そのものを問える**」ことを要求している。
公共財として、答えられない部分がどこかを利用者が知れることを設計の一部とする。

### B19: CQ2・CQ3の「年度」はレビューシートの年度であり、支払年度ではない

`budget:fiscalYear`(BudgetProject・Expenditureの両方が持つ)は、RSの
レビューシート自体が対応する事業年度である。**支出(Expenditure)の実際の
支払年度ではない** — Task 7の実測(task-7-review.md指摘7): RS 2025年度
シートの支出先ファイル(payee_payment_information)の金額は、実は
FY2024の執行実績である(事業ごとのΣ[23]とbudget_summaryのFY2024執行額
[19]の比較で、中央値がぴたり1.0000・完全一致32.3%を確認)。支出先ファイル
自身は支払年度を示す列を持たず、`[1]事業年度`は193,912行すべて'2025'
(=シートの年度)固定である。

したがってCQ2・CQ3の「年度」は**そのレビューシートが対応する事業年度**の
意味で問う。「その年度に実際に支払われた金額」という意味では読まない
(1年ずれる)。BudgetProjectの`budgetAmount`(当初予算)とExpenditureの
`amount_jpy`の合計を同じ年度の下で単純に比較すると、意味の異なる2つの値
(予算 vs 1年前の執行)を比べることになる点に注意する。この区別自体は
Task 7がスキーマのdocstringに記録済みで、Task 9は質問文にも明記して固定した。

### B20: 役割(`budget:role`)による事業内・受給者横断の合計は、Phase 1のCQの対象外にする

**実データでの検証結果**: `payee_payment_information`の[16]事業を行う上
での役割は、ブロック行(20,701件)で**distinct 16,196件**の自由記述であり
(2026-08-24実測)、「一次受給者」「間接補助事業者」「再委託」のような
小さな管理された語彙ではない。上位の値は`--`(299件)・空文字(208件)・
`-`(112件)・「補助事業の実施」(111件)・「事業の実施」(57件)・
「補助金等交付」(55件)・「間接補助事業者」(44件)・「事業実施主体」
(39件)・「予算配分」(38件)・「再委託」(29件)等だが、下位には
「光熱水料」「諸謝金」「出張旅費」のような**支出の使途区分としか
読めない値**も混在する — 同じ列が府省・事業によって「資金の流れの段」と
「経費区分」の両方の意味で使われている。

task-7-review.md指摘8は、事業内でΣ`core:amount_jpy`(全支出先の単純合計)
がbudget_summaryのFY2024執行額(合計)の正確に2.0倍/3.0倍になる事業があり
(構造的な二重計上。資金が「一次受給者」ブロックから「間接補助事業者」
「再委託」ブロックへ再計上される)、例として`間接補助事業者`(44行)・
`再委託`(29行)を挙げていた。

**実測(訂正: 前版は314件と記載していたが再現しない。正しくは221/24/245)**。
同じ2026-08-24の実データ、FY2024執行額>0の4,646事業を分母に、整数演算
(`total == 2*executed`/`3*executed`。丸め誤差を含む比較はしない)で数え直した:

```
exact 2.0 = 221   exact 3.0 = 24   計 245
exact 1.0 = 1,488   それ以外 = 2,877   Σ[23]==0 = 36
間接補助事業者/再委託 の除外で ==executed に戻った事業: 0 / 245
```

245はtask-7-review.md指摘8の値そのものであり、前版の「245件とは分母の
取り方が異なるため一致しない」という記載は誤りだった(分母は同一)。
執行額の取り方(strict/loose)×金額列([23]のみ/[23]\|\|[25])×判定
(exact/tol=1e-3)の8通りを試したが、287/27/314という組は再現せず、
いずれも245・373([23]をtol1e-3で見た場合。exact 2.0=335・3.0=38)・
1488(明細行[25]も加えると集計行[23]との二重加算で全事業がexact2.0側に
吸収され3.0側が0になる)・1898のいずれかになった。**「2値除外で回復=0」
という結論の向きは8通りすべてで再現した — 誤っていたのは数字だけだった。**

**論証の訂正**: 「間接補助事業者/再委託という2値の推測が外れた ⇒ どの
役割集合も定義できない」という前版の書き方は論理として成立しない(1組の
推測が外れたことは、他のどの組も外れることを意味しない)。本当の理由を
実測で確認した:

```
単一の役割値だけで ==executed に戻る事業: 222 / 245
その「勝つ役割値」のdistinct数: 330
最頻値の出現回数: 7('システム運用等の総括')。
  以下 '支出委任'(6) '-'(6) '補助金等交付'(5) '移替'(5) '執行機関'(5)
       '--'(4) '予算の移替'(4) '移替え'(4) …
```

245事業のうち222事業は**単一の役割値だけで正しい合計に戻る**。定義でき
ない本当の理由は「事業ごとに勝つ値が違う」こと——245事業に対して勝つ
役割値が330通りあり、最頻値でも7回しか出ない。固定の許可/拒否リストは
一般化しない:

| 規則 | 壊れた245件のうち直る | 正しい1,488件のうち壊す |
|---|---|---|
| 上位1役割のみ集計 | 7 | 1,488 |
| 上位5役割のみ集計 | 25 | 1,477 |
| 上位20役割のみ集計 | 50 | 1,454 |
| 間接補助事業者/再委託を除外 | 0 | 0 |

**ブロック構造軸の検証(裁定B24がレビューに指示していたが前版は未実施
だった。役割軸のみで結論していた)**。project_id=168を役割ではなく
[13]ブロック番号で組み直すと、隠れていた並列2連鎖が現れる:

```
block='A' name='農林水産省'      role='補助金等交付'        sum=  136,000,000
block='B' name='市町村'          role='補助対象事業の実施'  sum=  136,000,000
block='C' name='国土交通省'      role='補助金等交付'        sum=2,563,040,000
block='D' name='沖縄県・市町村'  role='補助対象事業の実施'  sum=2,563,040,000
executed FY2024 = 2,699,040,000  ( = A + C )
```

A→BとC→Dの2本の並列な連鎖で、それぞれが二重計上されている(前版が
「役割で畳んだ後の姿」だけを載せていたのは、この並列構造を隠す書き方
だった)。ブロック軸の規則を、**壊れた245件・正しい1,488件の両方で**測った:

| 規則 | 壊れた245件のうち直る | 正しい1,488件のうち壊す |
|---|---|---|
| 先頭ブロック(A)のみ集計 | 233 | **480** |
| 同額ブロックの畳み込み | 156 | 10 |
| 役割2値の除外 | 0 | 0 |

先頭ブロックは245事業すべてで`'A'`であり233/245(95%)を直すが、正しい
1,488事業のうち480件(32.3%)を壊す——exact1.0の事業の31.9%(474件)が
非ゼロブロックを2つ以上持つ(並列な一次ブロック)ため、**ブロック番号は
段(tier)を符号化していない**。「同額ブロックの畳み込み」は156/245を直し
10件しか壊さないが、(a) 89件は直らない (b) 金額の一致という値ベースの
推測であって一次資料が主張する構造ではないため、出典主義(推定を事実
としてemitしない)に照らして採らない。**役割軸と同じく、ブロック軸も
両側で測って閉じている**(諦めが早すぎるのではなく、この軸も実際に
閉じていることを確認した)。

**本当の出口(裁定B24がレビューに指示していた点)**: `jgkg.connectors.
rs_system.RS_GROUP_FILENAMES`はRSの配布ファイルを15グループ宣言している
が、レイクにあるのは5本(1-1/1-2/1-3/2-1/5-1)だけである。ブロック間の
親子関係(段の構造)は、推測するものではなくRSが別ファイルで配っている:
`payee_payment_block_connection`(`5-2_RS_{year}_支出先_支出ブロックの
つながり`。`rs_columns.RS_UNVERIFIED_GROUPS`に列挙済み、列は未照合)。

**定義(B20の履行として記録する結論)**: Phase 1のCQは、事業内・複数受給者
を横断する`core:amount_jpy`の合計(「この事業の実際の総支出額はいくらか」
「この府省の実際の総支出額はいくらか」のような問い)を**対象にしない**。
CQ2は`budget:budgetAmount`(RS自身が計算済みの当初予算(合計)の値で、
Expenditureを合計して作った値ではない)を使うため、この問題の影響を
受けず安全に含める。CQ3は特定の1法人「自身」が実際に受け取った額の一覧
であり、その法人が資金の流れの中でどの段にあるかによらず受け取った額は
受け取った額であるため、role除外を適用する必要も適用してはならない理由も
無い(適用すると受給者自身の実受領額を過少計上することになる)。
`budget:role`は保存され`queryable`である。fixtureのPROJECT_ROLE_DEMOで
素朴な合計が二重計上すること・`budget:role`での除外がこの最小例では効くこと
を`test_b20_naive_sum_double_counts_but_role_is_queryable`(CQ1〜10とは別の
専用テスト。10CQの一部ではないため`.rq`ファイルは作らない)で固定している。
ただし上記の実データ検証が示すとおり、この最小例が効くこと自体は
「実データ全般で通用する集計ルールが存在する」ことの証拠ではない
——効くのはこの2ブロックの最小例に限られる。Phase 1のCQ1〜10のどれも
`budget:role`を集計フィルタとして使わない。

**この結論は「原理的に不可能」ではなく、「5-1(取得済みの5ファイル)だけ
では不可能。段の構造は5-2にある。5-2の取得・列照合はPhase 2の課題」という
限定付きの結論である。** 将来、事業単位の実支出総額を問うCQを追加する場合は、
`5-2_RS_{year}_支出先_支出ブロックのつながり`を取得・列照合した上でブロック
間の親子関係をモデル化する必要がある(役割の文字列・ブロック番号からの
推測では解けないことは上記2つの表で両側から確認済み)。

なお、Task 7報告書がTask 11に渡した「合計≒執行額の突合を検証に使う」という
申し送りは、この実測(一致は1,488/4,646=32.0%のみ)により検証ゲートとして
使えない。撤回・再定義はprogress.md(裁定台帳)側の記録として別途反映される。

### B34: CQ2の`budgetAmount`は一般会計＋特別会計の合計。`ministry`は列5=政策所管府省庁

Task 11修正ラウンド2のレビューで指摘(観察1): CQ2の答え(厚生労働省
2025年度=91,789,031,491,000円)は**桁として正しい**(RS生CSVから独立に
集計して1円・1件も違わないことをレビュアが確認済み)が、この金額が
**一般会計と特別会計の合計**であることが、クエリのコメント・このファイル・
実測記録のいずれにも明記されていなかった。厚生労働省のFY2025一般会計
予算(≒34.8兆円)と比較する読者は約2.6倍ずれた解釈をする——**答えが
正しくても、読者が誤読するなら公開LODの一次成果物として欠陥である**、
という判断で明文化する。

**内訳(実測)**: 特別会計 71,174,383,135,000円(77.5%)+ 一般会計
20,614,648,356,000円(22.5%)= 91,789,031,491,000円。RSの
`budget_summary`の会計区分別明細行(列25「会計区分」)の合計が集計行
(列14「当初予算(合計)」)と完全一致することで確認した。**RSの
「当初予算(合計)」は会計区分を問わず全て含む**ため、CQ2をそのまま
「一般会計の予算」の代わりに使ってはならない。

**`ministry`(`budget:ministry`)は RS列5=政策所管府省庁から作る
(列6=府省庁ではない)。** `rs_columns.py`の`project_summary`/
`budget_summary`両スペックの`col["ministry_name"]`が列5(0-indexで
`full_header[5]`="政策所管府省庁")を指す。府省庁(列6)を主キーに数えると
事業数・総額がわずかに変わる(厚生労働省の例で1,175事業/91,788,753,850,000円
——列5版と1事業・277,641,000円の差)。「政策所管」(実質的な政策決定権限)を
採用したのは、法令の所管府省(CQ1・CQ5の`jurisdiction`)と対をなす概念として
一貫させるため——法令の所管も「実際に政策を所管する主体」を指しており、
組織上の事務分掌(府省庁)ではない。

### CQ6: 骨子との乖離

計画時点の骨子(`?e budget:recipient ?r . ?r a core:UnresolvedReference`)
は実装(`jgkg.rdf.emit.emit_budget`)と一致しない。未解決の支出は
`budget:recipient`自体を張らず(未解決ノードを値にしない)、別ノードが
`core:unresolvedFor`で支出を逆参照する(Task 4のB8: `core:UnresolvedReference`
はドメイン固有プロパティを宣言せず、値の側に置くと閉じたSHACLシェイプに
違反するため)。CQ6のクエリは実装に合わせて書いた(コメントに明記)。

さらに、recipientが無い支出は「未解決」だけではない。Task 7の
`BuildStats`が区別する3種類——**未解決**(照合を試みて失敗。
`core:UnresolvedReference`を持つ)・**束ね**(「その他」等への意図的な
集約)・**センチネル**(RSが個人・職員等に使う13桁のダミー法人番号
`9999999999999`)——をCQ6も区別する(4分類: resolved/unresolved/
bundled/sentinel。GROUP BYに事業を含め、事業単位のCOUNTで返す)。
束ね・センチネルを「未解決」に混ぜると、実際には照合の失敗ではないものを
失敗として過大に報告してしまう。
