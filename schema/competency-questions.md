# コンピテンシー質問(CQ)台帳

オントロジーは「良さそうなクラスを並べる」のではなく、**KGが答えられるべき
質問を先に文書化し、それに答えられるかで妥当性を判定する**(設計書§5.6)。
CQに答えられないオントロジーは、クラスがどれだけ整っていても不合格とする。

各CQには `queries/cq/` に対応するSPARQLがあり、`tests/test_competency_questions.py`
がテストとして実行する。**CQを追加したらテストも増える。**

### B19: CQ2・CQ3の「年度」はレビューシートの年度であり、支払年度ではない

`budget:fiscalYear`(BudgetProject・Expenditureの両方が持つ)は、RSの
レビューシート自体が対応する事業年度である。**支出(Expenditure)の実際の
支払年度ではない** — Task 7の実測(task-7-review.md指摘7): RS 2025年度
シートの支出先ファイル(payee_payment_information)の金額は、実は
FY2024の執行実績である(事業ごとのΣ[23]とbudget_summaryのFY2024執行額
[19]の比較で、中央値がぴたり1.0000・完全一致32.3%を確認)。支出先ファイル
自身は支払年度を示す列を持たず、`[1]事業年度`は193,912行すべて'2025'
(=シートの年度)固定である。

したがってCQ2・CQ3の「年度」は**そのレビューシートが対応する事業年度**の
意味で問う。「その年度に実際に支払われた金額」という意味では読まない
(1年ずれる)。BudgetProjectの`budgetAmount`(当初予算)とExpenditureの
`amount_jpy`の合計を同じ年度の下で単純に比較すると、意味の異なる2つの値
(予算 vs 1年前の執行)を比べることになる点に注意する。この区別自体は
Task 7がスキーマのdocstringに記録済みで、Task 9は質問文にも明記して固定した。

### B20: 役割(`budget:role`)による事業内・受給者横断の合計は、Phase 1のCQの対象外にする

**実データでの検証結果**: `payee_payment_information`の[16]事業を行う上
での役割は、ブロック行(20,701件)で**distinct 16,196件**の自由記述であり
(2026-08-24実測)、「一次受給者」「間接補助事業者」「再委託」のような
小さな管理された語彙ではない。上位の値は`--`(299件)・空文字(208件)・
`-`(112件)・「補助事業の実施」(111件)・「事業の実施」(57件)・
「補助金等交付」(55件)・「間接補助事業者」(44件)・「事業実施主体」
(39件)・「予算配分」(38件)・「再委託」(29件)等だが、下位には
「光熱水料」「諸謝金」「出張旅費」のような**支出の使途区分としか
読めない値**も混在する — 同じ列が府省・事業によって「資金の流れの段」と
「経費区分」の両方の意味で使われている。

task-7-review.md指摘8は、事業内でΣ`core:amount_jpy`(全支出先の単純合計)
がbudget_summaryのFY2024執行額(合計)の正確に2.0倍/3.0倍になる事業が
245件あり(構造的な二重計上。資金が「一次受給者」ブロックから
「間接補助事業者」「再委託」ブロックへ再計上される)、例として
`間接補助事業者`(44行)・`再委託`(29行)を挙げていた。

**この2値の除外だけでは二重計上は解消しない(実測で確認済み)。**
同じ2026-08-24の実データで、事業ごとに(a) 全ブロックの単純合計と
budget_summary FY2024執行額の比、(b) `間接補助事業者`/`再委託`ブロックを
除外した合計との比を計算した:

- 比が正確に2.0/3.0の事業: 314件(2.0が287件・3.0が27件。task-7-review.mdの
  245件とは分母の取り方が異なるため一致しないが、大きな二重計上が実在する
  こと自体は同じ結論)
- 上記314件のうち、`間接補助事業者`/`再委託`を除外して比が1.0に戻った事業:
  **0件**
- サンプル(project_id=168): 比を2.0にしている実際のブロックは
  `補助金等交付`(2,699,040,000円)と`補助対象事業の実施`(同額)の組であり、
  `間接補助事業者`/`再委託`はこの事業には出現しない

つまり「一次受給者ブロックか、資金が再計上されたブロックか」を区別する
役割ラベルの組は事業・府省ごとに異なり、文字列レベルで信頼できる
「集計対象とする役割の集合」を定義することはできない(検証スクリプトは
使い捨てのため未コミット。再現手順・出力の全量はtask-9-report.md参照)。

**定義(B20の履行として記録する結論)**: Phase 1のCQは、事業内・複数受給者
を横断する`core:amount_jpy`の合計(「この事業の実際の総支出額はいくらか」
「この府省の実際の総支出額はいくらか」のような問い)を**対象にしない**。
CQ2は`budget:budgetAmount`(RS自身が計算済みの当初予算(合計)の値で、
Expenditureを合計して作った値ではない)を使うため、この問題の影響を
受けず安全に含める。CQ3は特定の1法人「自身」が実際に受け取った額の一覧
であり、その法人が資金の流れの中でどの段にあるかによらず受け取った額は
受け取った額であるため、role除外を適用する必要も適用してはならない理由も
無い(適用すると受給者自身の実受領額を過少計上することになる)。
`budget:role`は保存され`queryable`である。fixtureのPROJECT_ROLE_DEMOで
素朴な合計が二重計上すること・`budget:role`での除外がこの最小例では効くこと
を`test_b20_naive_sum_double_counts_but_role_is_queryable`(CQ1〜10とは別の
専用テスト。10CQの一部ではないため`.rq`ファイルは作らない)で固定している。
ただし上記の実データ検証が示すとおり、この最小例が効くこと自体は
「実データ全般で通用する集計ルールが存在する」ことの証拠ではない
——効くのはこの2ブロックの最小例に限られる。Phase 1のCQ1〜10のどれも
`budget:role`を集計フィルタとして使わない。将来、事業単位の実支出総額を問う
CQを追加する場合は、役割の文字列ではなく構造(ブロック間の親子関係の
モデル化等)から解く必要があり、これは新しいCQのための設計課題として
残す(Task 7報告書の申し送りのまま)。

### CQ6: 骨子との乖離

計画時点の骨子(`?e budget:recipient ?r . ?r a core:UnresolvedReference`)
は実装(`jgkg.rdf.emit.emit_budget`)と一致しない。未解決の支出は
`budget:recipient`自体を張らず(未解決ノードを値にしない)、別ノードが
`core:unresolvedFor`で支出を逆参照する(Task 4のB8: `core:UnresolvedReference`
はドメイン固有プロパティを宣言せず、値の側に置くと閉じたSHACLシェイプに
違反するため)。CQ6のクエリは実装に合わせて書いた(コメントに明記)。

さらに、recipientが無い支出は「未解決」だけではない。Task 7の
`BuildStats`が区別する3種類——**未解決**(照合を試みて失敗。
`core:UnresolvedReference`を持つ)・**束ね**(「その他」等への意図的な
集約)・**センチネル**(RSが個人・職員等に使う13桁のダミー法人番号
`9999999999999`)——をCQ6も区別する(4分類: resolved/unresolved/
bundled/sentinel。GROUP BYに事業を含め、事業単位のCOUNTで返す)。
束ね・センチネルを「未解決」に混ぜると、実際には照合の失敗ではないものを
失敗として過大に報告してしまう。

### CQ9: 分類の境界

`core:unresolved_reason`が`OLD_MINISTRY`(2001年の中央省庁再編で廃止された
名称。`old-ministries.csv`記載)・`OBSOLETE_ORGANIZATION`(現存府省の
参照表にも旧省庁名の判定集合にも無いが政府機関の形をしている名称)の場合を
「旧・現存外の機関名のため未解決」とし、`NO_CANDIDATE`(政府機関の形にすら
見えない。抽出段の誤りを疑うべき警報)・`AMBIGUOUS`(参照表に同名が複数)を
「その他の未解決」として区別する(裁定B7・Task 4)。
