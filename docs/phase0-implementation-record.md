# Phase 0 実装記録 — 見つかった欠陥の型

Phase 0(データレイヤー基盤)の実装中に見つかった欠陥は **31件**あり、**5つの型**に収まった。
型ごとに「なぜ設計レビューでは見えなかったか」を記す。**同じ型を再発させないための記録である。**

実装の経緯そのもの(タスク分割・レビューの往復)は残していない。**再発防止に効く形だけを残す。**

---

## 型1: 実データでしか壊れない(5件)

fixture では現れず、テストは全部緑になる。**実データの規模・文字コード・分布で初めて壊れる。**

| 何が起きたか | 実測 |
|---|---|
| 解析でメモリが約5.5GBに膨らむ | 0.08MiB(ストリーミング) 対 145MiB(全載せ)。約1800倍 |
| Shift_JIS を UTF-8 として読み、全法人名が静かに文字化け | 「厚生労働省」→ `'�����J����'` |
| 500万件のオブジェクトと3000万トリプルをメモリに実体化 | 数GB規模 |
| Windows で隔離ファイルが NTFS 代替データストリームに消える | `exists()=True` なのに `iterdir()` は0バイト1個 |
| 名称重複1行でソース全体が隔離され、そのまま出荷される | ゲートが `exit 0` |

**対処の原則**: 実データの性質(規模・エンコーディング・OS固有の予約文字)は、fixture の外にある。
**「小さな入力で通る」ことは何の保証にもならない。** 規模と環境の想定を明示的に検算する。

---

## 型2: 空振りテスト(6件)

**テストがあること自体が安心材料にならない。** 3つの形で現れた。

- **対象0件で合格** — 空リストに対する `for` 文のアサートは常に通る
- **常に真で合格** — 否定形のアサート(「違反が無いこと」)は対象が0件でも通る
- **一覧を人間が手で書いているため、対象が増えると黙って抜け落ちる**

3つ目が最も執拗だった。**同型で3回起きた。** モジュール別のパラメータ化テストで、
片方のモジュール固有の名前をハードコードしていたため、もう片方を一切検査していなかった。
それを直した後、**3つ目のモジュールを追加したときに一覧へ足し忘れた。**
そのモジュールは公開対象そのもので、SHACL検証ゲートの実体だった。
**言語タグを72個消しても全テストが緑**という状態が生まれていた。

**対処の原則**:

1. 書いたテストについて必ず「**これは何があれば落ちるか**」を確認する
2. **わざと壊して、落ちることを実際に見る。** 出力を記録する
3. **検査対象の一覧を手で書かない。** ソースから導出し、
   「導出した集合」と「実ファイルの集合」を突き合わせるテストで守る

---

## 型3: 判定の部分適用・再発(4件)

**各タスクは正しい。横断的に見ないと分からない。**

ライブラリの既定値が想定と逆で、跨いだ問い合わせが常に空になる問題を1箇所で直した。
**他の箇所を忘れた。** さらに「この漏れに注意」と警告を書いた当のドキュメントで、
**同じパターンを再導入した。** 合計3回。

**対処の原則**: 判定を下したら、**その判定が適用されるべき全箇所を機械的に列挙する。**
「注意する」では足りない。**検査を書いて、漏れを失敗に変える。**

---

## 型4: 判定同士の矛盾 / 消費者のいない記録(5件)

**設計レビューでは矛盾が同時に見えない。**

- 出力側は言語タグ付きリテラルを書き、スキーマ側は型なし文字列を要求していた。**常に違反する**
- バージョンを記録して「実行側と照合する」とコメントに書いたが、**照合する経路が存在しなかった**
- 「ドメイン文字列は1箇所のみ」と決めて検査も入れたが、**実際は13箇所にあり、検査は1種類のファイルしか見ていなかった**

**照合されない記録は、記録の演技にすぎない。**
2つ目は3度直した。1度目は消費者がテストだけ、2度目は呼び出しが省略可能だった。

**対処の原則**: 記録を作ったら**その記録を読む主体を同時に作る。**
制約を書いたら**その制約を破ったときに落ちる検査を、対象を取り違えずに作る。**

---

## 型5: 実行系でしか出ない(7件)

**テストを1件も落とさずに、実行系が全く動かない状態が成立していた。**
2026-08-23 に `build.sh` → `serve.sh` → Fuseki → CQ を初めて通したとき、**5件が連続で出た。**
その間テスト115件は全部緑だった。

| 何が起きたか | なぜテストで出ないか |
|---|---|
| `build.sh` / `serve.sh` が `.env` を読んでいなかった。エラーは「`.env` に設定する」と案内するのに、設定してあっても落ちる | シェルスクリプトの実行そのものをテストしていない。docker compose は `.env` を自動で読むが bash は読まない |
| `apache/jena-fuseki` は **Docker Hub に存在しない**(リポジトリ自体が無い)。実在する `stain/jena-fuseki` は最新が 5.1.0 で 6.x が無い | イメージ名の実在を検査する手段がテスト内に無い |
| MSYS のパス変換。Git Bash が `/work/...`(コンテナ内のパス)を `C:/Program Files/Git/work/...` に書き換える | Windows でシェル経由で docker を呼んだときだけ起きる。CIは ubuntu |
| **TDB2 は読み取り専用ファイルシステム上では開けない**(`tdb.lock` を作れない)。設計書§6.3の「実行時は読み取り専用」をFSで担保する前提が成立しない | 実際にコンテナを起動しないと分からない |
| `/kg/sparql` が404。アセンブラの `fuseki:endpoint` に `fuseki:name` が無く、`/kg` 直下にしか束縛されていなかった。**`serve.sh` 自身が案内するURLが動かなかった** | エンドポイントに問い合わせないと分からない |

6件目は静的配信で出た(2026-08-23、`wrangler pages dev` に対する検証)。

**Cloudflare Pages は存在しないパスに index.html を 200 で返す。**
さらに `_headers` の `/def/*` 規則が**本文の内容に関係なく** `Content-Type: text/turtle` を被せる。
結果、オントロジーのファイルが欠落しても次のようになる。

```
$ curl -D - -o /dev/null http://localhost:8788/def/all.shacl.ttl   # ファイルを消した状態
HTTP/1.1 200 OK
Content-Type: text/turtle; charset=utf-8
```

**状態コードもContent-Typeも欠落を隠す。** 「200が返るか」「Content-Typeが正しいか」という
自然な検査は**両方とも合格する。** 捕まえたのは本文をパースする検査だけだった。

**対処**: `scripts/verify-site.py` に「本文がHTMLフォールバックでないか」を直接見る検査を足した。
配信物の検証は**ファイルの存在ではなく、利用者が解釈できるかで行う。**

7件目は公開後に出た。**検証スクリプトの出力が利用者の手元で文字化けした。**
Windowsで出力をパイプすると Python がロケールのコードページ(cp932)で書くためで、
`PYTHONUTF8=1` を付けて実行していた開発者(私)の手元では一度も起きなかった。
**§5.7 で生成物について同じ問題を記録し対処したのに、出力については見落としていた。**
呼び出し側に環境変数を要求せず、スクリプト側で `sys.stdout.reconfigure` で閉じた。

**対処の原則**: **「テストが緑」は「実行系が動く」を何も保証しない。**
完了条件に実行系が含まれるなら、**小さなサンプルでも一度は通す。**
通すまでは「動くと思っている」であって「動く」ではない。

一方で、この実行で**修正が効いていることも実出力で確認できた。**
CQ P0-4 は2つのソースについて別々の日付を返した(`国税庁 全件データ = 1970-01-01`、
`府省コード参照表 = 2026-08-22`)。**出典日付の捏造を直した効果が、テストではなく
エンドポイントへの問い合わせ結果として見えた。**

## すべてに共通する形 — 装置が黙る

全体レビューで出た Critical/Important 11件のうち **9件が「沈黙」**だった。
SHACL検証ゲート・CQ・隔離処理・バージョン照合が、それぞれ特定条件で黙る。

最も重かったのは**設計書自身の制約と、そのために作った検査**である。
ドメインを差し替えるとデータは新しい名前空間で書かれるのに検証対象は旧名前空間のままになり、
**一致するシェイプが無いので全グラフが「適合」になる。ゲートが素通しになり、しかも緑。**

**目的は「動く」ことではなく「壊れたときに鳴る」ことである。**

## 最も見えにくかった形 — 円環の内側で照合していた

実行前スキャンにこう記録していた。

```
Task 5: OK。fixtureのCSV列位置とTask 6のCOL定数が整合
```

**照合したのは、自分で書いた fixture と、自分で書いた定数である。**
どちらも同じ思い込みから出ているので、一致するのは当然だった。
**一次資料は円環の外にあり、一度も触れていない。**

これは空振りの一段上にある。空振りは「テストが何も検査していない」だが、
これは**「テストは検査しているが、検査対象が自分の仮定のコピーである」**という形で、
**テストを厳しくしても検出できない。**

同じ円環は修正作業中にも再発した。予約文字の一覧を定数から導出してテスト入力を組み立てたため、
**定数から1文字外すと入力からも消えて、テストは通り続けた。**
一覧をテスト側に独立して持ち、定数がそれを包含していることを主張する形に変えて解決した。

**対処の原則**: 検査対象と検査基準が**同じ出所から来ていないこと**を確認する。
一次資料に当たれない場合は、**当たれていないことを明記する。**

**解決(2026-08-23)**: 一次資料(全件データUnicode版CSV、`00_zenkoku_all_20260731.csv`)を
取得して照合した。**COL は実際に誤っていた** — `kind_code=5` の位置には変更年月日(日付)が、
`prefecture=12` の位置には空欄が入る。正しくは kind=8 / prefecture=9 / city=10 / street=11、
総列数30。

**そして円環の外の守衛は設計どおりに鳴った。** 誤ったCOLのまま実データを流すと:

```
ColumnLayoutError: 法人種別コードが3桁でない行が多すぎる。
法人種別の列(5)がずれている疑いがある。(非空行=5000 取り込み=5000 法人種別3桁=0)
```

fixture のテストは(円環なので)全部緑のままだった。**「fixtureで緑」と
「実データで正しい」の間の溝を埋めたのは、形の検査(3桁コード)と収量チェックだけだった。**
修正後は実データ5000行が全件取り込め、実在の国の機関が正しく抽出された。
