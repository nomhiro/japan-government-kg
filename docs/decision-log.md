## なぜ公開するか

このプロジェクトの目的は公共財(OSS + LOD)である。政府データの構造を扱う以上、
**そのオントロジーをどう決めたかという判断過程も記録の一部**だと考えている。
実データに当てて初めて分かった落とし穴は、同じものを作ろうとする人にとって
結論より有用かもしれない。例:

- 法令番号から府省を導く経路の失敗と、そこから分かった分類の粒度
- `tdbloader` が置換でなく追記であること
- 全法人を入れると 13.8 GiB になり、支出先に限れば 429 MiB で収まること
- 政府標準利用規約が2024-07-05に公共データ利用規約(第1.0版)へ改訂され廃止されていたこと
- 旧省庁の継承が「対応表として公布された政令」に機械可読で存在すること

**自分の誤りもそのまま残してある。** 裁定の文言が守ろうとした対象を除外していた例
(B16 → B36)、公開物の検査が対象一覧を手書きしていたため陳腐化を検出できなかった例(B40)、
完了寸前のビルドを壊した例(Cブロック末尾)などである。

**Ruling B3: sh:class とR1(最も具体的な型のみ)の構造的衝突は、validate.py に ont_graph を渡して解く。
ただし inference='rdfs' は使わない(閉じたシェイプを壊すため)。効かなければ range 縮小に切り替える。**
実装者の発見(実測済み): `law:jurisdiction` の `sh:class org:Organization` は、emit が R1 により
`org:Ministry` 型しか付けないため**原理的に不合格になる**。subClassOf の知識は all.owl.ttl にしか
無く、validate.py はそれを渡していない。グラフ跨ぎではないことも同一グラフ実験で訂正済み。

裁定の根拠:
(a) inference='rdfs' の全面適用は**危険**: 推論が `?m a org:Organization` を実体化すると、
    Organization の閉じたシェイプが Ministry インスタンスに適用され、ministryCode が
    「宣言されていないプロパティ」として**偽の違反**を出す(R24 の二重シェイプ問題の推論版)。

(c) range の縮小(jurisdiction→Ministry, recipient→Organization)は動くが、オントロジーの
    表現力を落とす。将来の非府省の所管・非法人の受領者で再変更になる
(d) **ont_graph=all.owl.ttl を inference なしで渡す**: SHACL 仕様の sh:class は
    rdf:type/rdfs:subClassOf* で判定するため、subClassOf の知識だけあれば足りるはず。
    型の実体化が起きないので閉じたシェイプに触らない。**これを第一候補として実測させる**

(2) **閉じたシェイプの偽violationが出ない**(ministryCode を持つ Ministry が通り続ける)
(3) 逆に「Organization でも Ministry でもない型」の値は落ちる(sh:class が死んでいないこと)

range 縮小(c)に切り替える(schema 2ファイルの変更+再生成)。判定は実測が下す

**controllerの診断が間違っていた。**

controllerは cq06(149.875秒)の原因を「73,919件に対する3重のOPTIONAL左結合で、
分類を不在から推論しているから」と診断し、**分類を emit 時に明示して単一結合にする**
裁定を出した(D-2)。実装は完了し、クエリは確かに単一結合になった:

```sparql
SELECT ?project ?category (COUNT(?e) AS ?count) WHERE {
  ?e a budget:Expenditure ; budget:project ?project ;
     budget:recipientMatchCategory ?category .
} GROUP BY ?project ?category ORDER BY ?project ?category
```

**それでも 175.250 秒だった**(旧149.875秒より遅い)。

### controllerが実測で判別した

同じFusekiに対して連続実行:

```
1回目: 8,151行 / 175.250 秒
2回目: 8,151行 /   0.812 秒
3回目: 8,151行 /   0.953 秒
```

**200倍の差。原因はページフォルトである。**

cq06は**74,000件の支出部分に最初に触るクエリ**で、cq01〜cq05は法令・府省・事業
(小規模)しか触らない。**索引の大部分(428.5 MiB)をページインするコストが
cq06に集中して現れていた。**

### 何を学んだか

**「他のCQは8.75秒以内なのにcq06だけ150秒」という観測から、
クエリ固有の問題だと推論したのが誤り。** アルファベット順の実行で
**cq06が大きい部分に最初に触る**という順序の効果を見落としていた。

**正しい判別方法は「同じクエリを2回流す」**。1回で結論してはいけない。

### D-2の materialization は維持する

**レイテンシは直さなかったが、裁定B42の脆さ(分類を不在から推論する構造)を
直したのは本来の価値であり、そこは達成している。**
**性能の理由付けが間違っていただけ。** 明示された分類は:
- 読み手が「何が無いか」から推論しなくて済む
- 番兵と実在しない法人番号を区別できないことが名前で分かる
- 新旧照合(裁定B54の欄を再利用)でドリフトを検出できる

### 実行時への影響(D-3以降で反映する)

1. **API層は起動時にキャッシュを温める必要がある。**
   代表的なクエリを1本流して支出部分をページインする。
   **D-1で測った「コールドスタート14秒」はFusekiが応答を返すまでで、
   索引がページインされるまでを含んでいなかった。**

2. **プラットフォームの判断が逆転しうる。**

| 一時領域 | メモリ | 初回クエリ |
|---|---|---|
| **tmpfs** | 実測 + 428.5 MiB | **ページフォルトなし = 速い** |
| 実ディスク | 539〜627 MiB | **初回に最大175秒** |

**controllerは「tmpfsはメモリを食うので不利」とD-1のブリーフに書いたが、
「索引が最初からRAMにある」という利点でもある。**
メモリを1 GiB程度に上げてtmpfsを使う構成が、初回クエリの速さでは有利。
**測る前は欠点だと思っていたものが、利点でもあった。**

## 裁定 B59: `/search` の返すIDは `/entity/{id}` が受け取れない(実データ検証で発見)

**667件のテストが緑のまま通り抜けた欠陥。** D-3のAPI層を**初めて実KG
(884,052クアッドのFuseki)に対して動かして**見つかった。

### 実測(controller。`docker restart` 後、温まった状態)

```
search が返す id : https://jgkg.norr-tech.com/id/budget/2025/2841
(A) id をそのまま get_entity_detail に渡す → None   (0.016秒)
(B) {base_uri}/id/ を剥がして渡す         → 応答あり (0.250秒)
    型=BudgetProject / 属性4種 / 関係グループ3
      Expenditure / UnresolvedReference / Ministry
```

`search_entities` は `SearchHit(id=entity, ...)`(`queries.py:244`)で
**完全IRI**を束縛する。`get_entity_detail(client, base, id_path, limit)` は
`entity_uri = f"{base_uri}/id/{id_path}"` を組み立てるので、
**`{base_uri}/id/` を除いたパス形**を期待する。完全IRIを渡すと
`.../id/https://.../id/budget/2025/2841` になり、必ず0件=`None`。

### なぜテストが捕まえなかったか

**2本のエンドポイントが単体でしかテストされていない。**
`tests/test_api_entity.py` は `"org/0000000000000"`・`PROJECT_CORE_ID` など
**パス形を全て手書き**しており、**検索結果の `id` を詳細に渡すテストが1本も無い。**
各エンドポイントは正しく動く。**合成だけが壊れている。**

これは既知の欠陥型の新しい形である——空虚なテスト(型2)ではなく
**「単体では真、合成では偽」**。再発欠陥の一覧に加える。

### 裁定

**(1) `id` は完全IRIのまま維持する。** このプロジェクトの成果物はKGであって
アプリではない(記憶: kg-not-app-is-the-deliverable)。IRIはLODの同一性
そのものであり、API都合で格下げしない。

**(2) 導出フィールドを `EntityRef` に足す**(`SearchHit` ではなく)。
`queries.py:383` は関係の相手側を `EntityRef(id=other, ...)` で組み立てて
おり、**詳細→関係の相手→詳細**の遷移が同じ欠陥を1ホップ先で繰り返す。
検索ヒットだけ直すと、D-5のクリック遷移に同じバグを渡す。

**(3) 導出ヘルパーは1本。** 構築箇所は3つ(`queries.py:244` SearchHit /
`383` 関係の相手 / `398` EntityDetailResponse。`EntityDetailResponse` は
`EntityRef` の派生ではないので個別に必要)。**箇所ごとに剥がし処理を
手書きしたら再発欠陥1(導出すべき値の手書き)そのもの。**

**(4) ルートで完全IRIを受け取れるようにはしない。** `/entity/{id:path}` に
`https://...` を渡す形は、パスセグメント中の `//` がプロキシやHTTP
クライアントに畳まれる。**TestClientでは通り、実HTTP経由で落ちる**種類の
脆さになる。**正規形を1つに保つ。**

**(5) 欠けているゲートはアプリ層の合成テスト**:
`GET /search` → `hit` の導出フィールド → `GET /entity/{それ}` → 200 かつ
`id` が一致。**関数レベルではなくアプリレベル**で書く(`:path` ルート
コンバータ自身が検証対象に入る)。**現行コードに対して先に書いて、
落ちるところを見せること。**

## 裁定 B60: 温めが誤った索引領域を温めていた(controllerの指示が原因)

**裁定B55の対策(起動時の温め)は、実測すると効いていなかった。**

### 実測(controller。`docker restart` 直後 = ラベル領域は真に未読)

```
warm_up()                :   4.734 秒
search('厚生', limit=10)  : 111.219 秒   ← 温めた後の最初の検索
```

温まった後:

```
search('厚生')   : 0.312 秒
search('国土')   : 0.625 秒
search('デジタル'): 0.609 秒
search('年金')   : 0.703 秒
```

**温めは支出述語(`budget:Expenditure`/`project`/`recipientMatchCategory`)を
温めるが、検索が触るのは `skos:prefLabel` を全型横断で走る別の領域である。**
`warm_up()` が4.734秒で終わったこと自体が証拠——B55が175秒を測った同じ
領域が4.734秒で済んだのは、**その領域が既に常駐していた**からで、
真に未読だったのはラベル領域(111秒)だけだった。

### 原因は controller の指示である

D-3ブリーフに controller はこう書いた:

> 索引の**支出部分を**ページインする代表的なクエリを1本流す仕組みを
> 入れてください。**入れないと、最初のリクエストが最大175秒かかります**

**cq06で観測した領域を、APIが触る領域だと決めつけて書いた。**
APIの2本のエンドポイントは支出述語を触らない。**実装者はブリーフの通りに
正しく作った。** 温める場所の指定が誤っていた。

### 裁定: 温めのクエリを手書きしない

`warm_up()` は **`search_entities(client, base_uri, <語>, 1)` を自分で呼ぶ。**
温める領域を**実際のコード経路から導出**する形にすれば、二度とずれない
(手書きのSPARQLを置くのは再発欠陥1の別の衣装である)。
`_warmup_query` の支出クエリは削除する——**現状どのエンドポイントもその
領域を走らない。**

**語の選び方は被覆に影響しない。** `_build_search_query` は
`ORDER BY ?label ?entity` を持つため、**LIMITの前に全件の計算が強制される**
——どの語でもラベル領域は全走査される。実測がこれを裏づけている
(111秒の後、**別の語**も0.6〜0.7秒)。**ただしこの前提は明記すること**:
将来 ORDER BY を外すか全文索引を入れると、**温めの被覆の根拠が消える。**

**付随して記録すべき規模の限界**: 検索は1リクエストあたりラベル全走査で
ある(O(ラベル数))。884,052クアッドで温まった状態0.3〜0.7秒は許容だが、
**データが増えると線形に悪化する。** 全文索引(Jena text / Lucene)は
将来の課題として記録する。

## 裁定 B61: B55の175秒/111秒は Windows バインドマウント越しの計測である

> **この裁定は B62 で一部撤回されている。** 「実Linuxファイルシステム上なら
> 速い可能性が高い(未実測)」および「起動時に111秒かかり起動プローブを
> 超える」という記述が誤りである——**発見7が既に58倍差を実測しており**、
> 正しい配備では初回読みは数秒に収まる。**下の本文はその誤りを含んだまま
> 残してある**(時系列の記録として)。**B62を必ず併せて読むこと。**

**B55の数字に前提が付く。** `docker-compose.yml` は TDB2 索引を
`./data/artifact/current/tdb2`(Windowsパス)からバインドマウントしている。
Docker Desktop/WSL2 ではこれは 9p/virtiofs 越しになる。

**428.5 MiB に 175秒 = 約2.4 MiB/s。** ローカルSSDのページフォルトでは
出ない数字で、**ファイル共有越しの往復**の特徴である。**したがって
「ページフォルト」というB55の説明は、より正確には「マウント越しの初回読み」
である。** 実Linuxファイルシステム上の同じ索引は桁違いに速い可能性が高い
(未実測——D-6で測る)。

### 温めについての含意(D-6の入力として決定的)

**温めはコストを消さない。起動時に移すだけである。** ラベル領域の初回読みが
111秒なら、**`warm_up()` が起動時に111秒かかる。** 多くのプラットフォームは
起動(readiness)プローブがそれを待たず、**コンテナを落として再起動する
ループに入る。**

**したがって D-6 の判断は「温めがあるから大丈夫」ではない。**

| 索引の置き場所 | 初回読み | 起動プローブ |
|---|---|---|
| Windowsバインドマウント(現在の開発環境) | 111〜175秒 | **超える** |
| 実Linux FS / イメージに焼き込み | 未実測 | 要測定 |
| tmpfs(B55の表) | ページフォルト無し | 通る。メモリ +428.5 MiB |

**未解決: 直した温めがコールドで何秒かかるかは未測定である。**
測るには真のコールドが必要で、**`docker restart` では足りない**
(VMのページキャッシュが残る。上の4.734秒がその証拠)。真のコールドは
`wsl --shutdown` かVM内の `drop_caches`。**`wsl --shutdown` は他の並行
ジョブを巻き込むため controller は単独で実行しない。** D-6で、
プラットフォーム判断と併せて測る。

**この節が済むまで「温めは直った」と報告してはならない。**
言えるのは「**エンドポイントが実際に走る領域を、コード経路から導出して
温めるようになった**」までである。

振れている)。

**(5) B61の「未実測」という記述は誤りとして撤回する。**

コールドで何秒か」だけ**であり、それは配備先には無関係な数字なので、

## 裁定 B63: デプロイ後の検証は「古い内容がまだ有効に載っている」を通してしまう

**controllerがA-4で作ったCDのゲートに穴がある。**

`.github/workflows/ci.yml` の `deploy` ジョブは配信後に
`scripts/verify-site.py` を回す(6回・10秒間隔)。`site-check.yml` も
1日1回同じスクリプトを本番URLに対して回す。

### verify-site.py が検査していること

- `/def/*` の `Content-Type` が `text/turtle` で始まる
- **HTMLフォールバックでない**(`_is_html_fallback`。2026-08-23の事故対策)
- **Turtleとしてパースできる**
- **名乗っている名前空間が正しい**

### 検査していないこと

**配信されている内容が、いま手元でビルドした内容と同じかどうか。**
`sha256` の比較が1箇所も無い。

**したがってこの状況を全て通す**:

| 状況 | 現在の検査 |
|---|---|
| `/def/law` が消えた | **落ちる**(status) |
| `/def/law` がHTMLを返す | **落ちる**(`_is_html_fallback`) |
| `/def/law` が壊れたTurtle | **落ちる**(パース) |
| **`/def/law` が3日前の版のまま有効なTurtleを返す** | **通る** ← 穴 |
| **`wrangler pages deploy` が黙って何も上げなかった** | **通る** ← 穴 |

**スキーマに新しいクラスを足して、生成物をコミットして、配信が静かに
失敗した場合** —— 古い `/def/core` は依然として有効なTurtleで、正しい
名前空間を名乗り、`text/turtle` で配信される。**全ての検査が通る。**

**これは「デプロイが成功したこと」を検証していない。**
「**何かが載っていること**」を検証している。
**このセッションが繰り返し扱ってきた「正しくない理由で通る検査」
(再発欠陥5: 循環検証)そのものである。**

### 裁定: ハッシュ比較を足す。新しい仕組みは要らない

**`deploy` ジョブは配信の直前に `site/` をビルドしている。**
配信後に `/def/*` を取得して **`site/def/*` と sha256 を比べる**だけでよい。
**追加の基盤は不要で、比較対象は既に手元にある。**

`site-check.yml` も main をチェックアウトして uv を入れているので、
**同じビルドを回して同じ比較ができる。**

### 実装上、先に確かめるべきこと(推測で書かないこと)

**配信された本文がディスク上のファイルとバイト同一である保証を、実際に
確認してから比較を書くこと。** 静的配信なら同一のはずだが:

- gzip等の転送エンコーディング(HTTPクライアントが復号するか)
- 末尾改行やBOMの扱い
- Cloudflare側の変換の有無

**同一でないなら、ハッシュ比較は不安定な検査になり、
「たまに赤くなるので無視される検査」に退化する** ——
それは検査が無いより悪い。**まず1本のファイルで実測すること。**

### 競合について

`site-check.yml` は06:00 JSTに回る。その直前に main へpushがあると
**配信中のずれを掴んで偽陽性になりうる。**
`deploy` ジョブの検証と同じく**数回のリトライ**で吸収する
(配信は1分以内に終わる)。**リトライしても不一致なら落とす。**

### この裁定の位置づけ

**A-4のCD導入時に controller はこのゲートを「配信の検証」として説明した。**
実際には「何かが載っていることの検証」だった。**A-4の報告は過大だった。**
`site-check.yml` の冒頭コメントは
「**ここが今捕まえるのは自分たち以外を原因とするずれである**」と書いているが、
**自分たちを原因とするずれ(配信が黙って失敗する)も捕まえられていない。**
そのコメントも直すこと。

### 前提の実測(controller。2026-08-28、本番URLに対して読み取りのみ)

**バイト同一性は成立する。**

```
/def/core.owl.ttl     一致 / 16,647B / Content-Encoding=(なし)
/def/core.shacl.ttl   一致 /  9,362B / Content-Encoding=(なし)
/def/core             一致 / 16,647B / Content-Encoding=(なし)  ← 拡張子なしエイリアス
/def/all.owl.ttl      一致 / 53,745B / Content-Encoding=(なし)
/robots.txt           一致 /    352B / Content-Encoding=gzip    ← 透過復号でも一致
```

**したがってハッシュ比較は安定した検査になる。** 付随して分かったこと:

- **拡張子なしのエイリアス `/def/core` は `core.owl.ttl` を返す**
  (`.shacl.ttl` ではない)。**この対応を手書きしないこと**
- **`Content-Encoding: gzip` で配信されるファイルがある。**
  比較するクライアントは**透過復号するもの**を使う(httpxは既定で復号する)。
  生バイトを取る実装にすると gzip のファイルだけ不一致になる

### 設計の要求: URL↔ファイルの対応を導出すること

**比較対象を手書きのリストにしないこと。** 裁定B40が同じ欠陥を扱っている
(`verify-site.py` に `MODULES = ("core","org","all")` が直書きされていて、
モジュールを足しても検査が増えなかった)。

**`site/` を再帰的に走査して各ファイルのURLを導出し、全件を比較する形にする。**
そうすればモジュールを足したときに検査対象が自動で増える。
拡張子なしのエイリアスは `site.py` が生成規則を知っているので、
**その規則を参照する**(再実装しない)。

## 裁定 B65: HTMLはハッシュ比較できない(Cloudflareがスクリプトを挿入する)

## 裁定 B66: 公開オントロジーに RFC 3986 非適合のIRIが8件ある(列挙型の許容値)

**公開物の欠陥。controllerが本番URLに対して実測(2026-08-28)。**

`https://jgkg.norr-tech.com/def/all.owl.ttl`(および `core`/`budget`)に、
**`#` が2つあるIRIが8件**ある:

```
<https://jgkg.norr-tech.com/def/budget#RecipientMatchCategoryEnum#bundled>
<https://jgkg.norr-tech.com/def/budget#RecipientMatchCategoryEnum#resolved>
<https://jgkg.norr-tech.com/def/budget#RecipientMatchCategoryEnum#sentinel_or_nonexistent_houjin_bangou>
<https://jgkg.norr-tech.com/def/budget#RecipientMatchCategoryEnum#unresolved>
<https://jgkg.norr-tech.com/def/core#UnresolvedReasonEnum#AMBIGUOUS>
<https://jgkg.norr-tech.com/def/core#UnresolvedReasonEnum#NO_CANDIDATE>
<https://jgkg.norr-tech.com/def/core#UnresolvedReasonEnum#OBSOLETE_ORGANIZATION>
<https://jgkg.norr-tech.com/def/core#UnresolvedReasonEnum#OLD_MINISTRY>
```

いずれも `a owl:Class` として宣言され、`ns1:permissible_values` と
`owl:unionOf` から参照されている。**列挙型の許容値すべてが該当する。**

### なぜ不正か

RFC 3986 §3.5:

```
fragment = *( pchar / "/" / "?" )
pchar    = unreserved / pct-encoded / sub-delims / ":" / "@"
```

**`#` は `gen-delims` に属し、`pchar` にも `sub-delims` にも含まれない。**
したがってフラグメントに `#` は現れられず、**2つ目の `#` を持つ文字列は
URIではない。**

Turtle の `IRIREF` 字句規則は制御文字・`<>"{}|^` バックスラッシュだけを
除外するので**`#` を通す** —— つまり**Turtleとしてはパースでき、
IRIとしては非適合**という状態である(Turtle仕様は「IRIは絶対IRIまたは
相対IRI参照でなければならない」と定めている)。rdflibは通す。
**厳格なツールは拒否するか、2つ目の `#` で切り詰めうる。**

**切り詰められた場合の具体的な害**: `budget` の4つの許容値が
すべて `budget#RecipientMatchCategoryEnum` に**黙って畳まれる**
(4つが1つになる)。**気づきにくい壊れ方である。**

### 影響範囲は限定的である(実測で判別済み)

| 対象 | 二重#のIRI |
|---|---|
| `/def/*.owl.ttl` | **8件** ← ここだけ |
| `/def/*.shacl.ttl`(3本を確認) | **0件** ← 検証ゲートは見ていない |
| **KGデータ(Fuseki 884,052クアッド)** | **0件** |
| **`kg.nq`(配布物)** | **0行** |

**`budget:recipientMatchCategory` の値は列挙IRIではなくプレーンリテラルである**
(実測):

```
[literal] resolved                              56,607 件
[literal] sentinel_or_nonexistent_houjin_bangou  9,982 件
[literal] bundled                                7,326 件
[literal] unresolved                                 4 件
```

**したがってKGをダウンロードする消費者には影響が無い。**
**壊れているのは語彙の公開物だけであり、それを参照するものはどこにもない。**

### 副産物の検証(記録する価値がある)

**4分類の合計 = 56,607 + 9,982 + 7,326 + 4 = 73,919 で支出件数と完全一致。**
**すべての支出がちょうど1つの分類を持ち、4分類が厳密に分割している。**
D-2のmaterializationは**取りこぼしも重複も無い**(裁定B42が直そうとした
「不在からの推論」が構造的に消えていることの独立した確認)。

### 裁定

**(1) 直す。** このプロジェクトの成果物はオントロジーである
(記憶: kg-not-app-is-the-deliverable)。**その公開物にIRIとして不正な
ものが8件あるのは、成果物の欠陥である。** 参照しているものが無いので
**破壊的変更のリスクは実質無い**(現状の形が既に不正なので、
「不正なIRIへの参照が壊れる」ことは論理的に問題にならない)。

修正は LinkML 側で許容値のURI生成規則を明示することになる
(`schema/*.yaml` の列挙定義)。**`schema/generated/*` が変わるので、
バイト同一性の正規化と公開物の差分が発生する。** 生成物はコミットする
方針なので、生成→コミット→CD配信の一巡を通す。

**(2) 構造的な対策を入れる(一度きりの修正で終わらせない)。**
**公開物の全IRIがRFC 3986に適合していることを検査に加える。**
`scripts/verify-site.py`(または生成物の検査側)に入れる。
**一度きりの修正だけでは、LinkMLのバージョンや新しい列挙型で再発する** ——
記憶が「LinkML採用の落とし穴: URI既定値の不整合が最大の罠」と記録している
とおりの族である。

**(3) 優先度は中。** 消費者への実害が無く、D-4/D-5/D-6より後で良い。
**ただしB63/B64/B65の対策と同じファイル(`verify-site.py`)を触るので、
その作業に相乗りさせるのが最も安い。**

## 裁定 B67: 温めの語は空文字列で正しい(controllerの推論の訂正)+ 温めはメモリ圧で減衰する

**controllerは測らずに断定し、また間違えた。**

D-3修正の実装者は `_WARMUP_SEARCH_TERM = ""`(空文字列)を選んだ。
controllerは実データで `warm_up()` が **22.313秒**かかるのを見て、
「`CONTAINS(label, "")` は全ラベルに一致するので `ORDER BY` が全件を
ソートし、5つのOPTIONALを全件に評価する。**それが22.3秒の正体で、
温めとしては無駄な費用である**」と診断し、普通の語に変えるべきだと考えた。

### 実測(温まった状態。limit=1)

```
空文字列(現在の実装)   1.437秒 / 1.204秒   件数=1 truncated=True
一致0件の語           0.234秒 / 0.250秒
普通の語「厚生」        0.281秒 / 0.453秒
```

**空文字列の追加費用は約1秒であり、22.3秒ではない。**
**controllerの診断は誤り。**

### 22.313秒の本当の原因

**その時点で索引が部分的にコールドに戻っていた。**
直前に実装者が全テストスイートを走らせており、メモリ圧で
ページが追い出されていた。**同じ呼び出しが、温まった状態では1.2〜1.4秒。**

**これ自体が重要な発見である: 温めは一度払えば終わりではなく、
メモリ圧で減衰する。**

**D-6への含意**: **温めに頼る設計にしてはならない。**
索引の置き場所の速さ(実Linux FS / イメージへの焼き込み / tmpfs)で
解決する話であって、起動時に1本流せば済む話ではない。
同一ホストで他のプロセスがメモリを使えば、**稼働中に再びコールドになる。**
裁定B62の「D-6は配備先の構成で実測すること」がさらに重要になる。

### 裁定: 空文字列を維持する

**実装者の判断が正しい。** 理由:

- 空文字列は**5つのOPTIONALの領域も全件分温める**
  (`law:lawNum`・`org:prefectureName`・`org:cityName`・
  `budget:fiscalYear`・`budget:ministry/skos:prefLabel`)。
  **これらは `/search` の要約導出と `/entity/{id}` が実際に読む領域である**
- 追加費用は温まった状態で約1秒。**温める範囲の広さに対して安い**
- 一致0件の語より0.25秒しか高くない一方、**温める領域が明確に多い**
- 語の選択に「実データに何が存在するか」の仮定が入らない
  (普通の語は、将来データが変わって一致0件になっても気づけない)

**controllerは変更を要求しない。**

### 併せて記録する規模の限界

## 裁定 B69: `/entity/{id}` が、KGに存在しないIRIを `id` として返す(8,555エンティティ)

**裁定B59を直した直後に、同じ族の欠陥が1フィールド隣で見つかった。**
controllerがAPIの**実HTTPサーフェス**(FastAPIのルート。`:path` コンバータ)を
実Fusekiに対して初めて通して発見した——B59の検証は `queries.py` の
**関数呼び出し**で行っており、ルートを通していなかった。

### 実測(controller、2026-08-28。全境界を観測)

```
KG内の真のIRI(searchが返す): .../2841/%E2%91%A0%E5%9B%BD%E6%B0%91...
                                    (= ①国民年金法等の一部を改正する法律 附則第34条第4項)

クライアントの渡し方3通り        status  投げたIRIが真のIRIと一致  応答のidが真のIRIと一致
(1) id_path を生のまま            200          True                    False
(2) パス片を正しくエンコード      200          True                    False
(3) デコード形(日本語)を渡す      200          True                    False
```

**引きは3通りすべてで堅牢である**(Starletteが1回デコードし、`sparql_iri` が
再エンコードするため、どの入り方でも同じ正しいIRIに収束する)。
**壊れているのは「応答が報告する `id`」だけである。**

```
応答の id: https://jgkg.norr-tech.com/id/unresolved/budget-basis-law/2025/2841/①国民年金法等の…
           ↑ このIRIはKGに存在しない(実測: 主語に持つトリプル 0 件。
             エンコード形は 5 件)
```

### 原因: 同じ値を2つの規則で作っている

`queries.py` の `get_entity_detail`:

```python
entity_uri = f"{base_uri}/id/{id_path}"      # 応答の id に使う(素の文字列連結)
entity_iri = sparql_iri(base_uri, id_path)   # クエリに使う(セグメントごとに再エンコード)
```

**ASCIIだけの `id_path` では一致し、エンコードが必要な文字があると分岐する。**

`sparql_iri` のdocstringはこう主張している:

> 正規のIDに対しては**素通りするだけで実質的に変化しない(往復が壊れない)**

**8,555エンティティについてこの主張は偽である。** `quote` は素通りせず、
Starletteがデコードした文字を**再エンコードして戻している**——
そのおかげでクエリは当たるが、**素の文字列連結の側だけが取り残される。**

### 影響範囲(実測)

`%` を含むIRIを持つ型:

| 型 | 件数 |
|---|---|
| `LawRevision` | **7,795** |
| `UnresolvedReference` | **742** |
| `AbolishedGovernmentOrgan` | **18** |
| **合計** | **8,555** |

**`UnresolvedReference` の 771 件中 742 件(96%)が該当する。**
非ASCII文字を生で含むIRIは0件——**emit側は一貫してパーセントエンコードしている。
データは自己整合であり、APIだけが整合していない。**

| エンドポイント | 報告する `id` |
|---|---|
| `GET /search` | **真のIRI**(SPARQLの行そのまま) |
| 関係の相手側 `EntityRef.id` | **真のIRI**(同上) |
| **`GET /entity/{id}`** | **存在しないIRI** |

**2本のエンドポイントが、同じエンティティの同一性について食い違っている。**

### なぜ重いか

**このプロジェクトの成果物はKGとオントロジーである**(記憶:
kg-not-app-is-the-deliverable)。**LODではIRIが同一性そのものである。**
`/entity/...` の `id` を受け取った消費者が、それをダウンロードした
`kg.nq` で引くと**何も見つからない。**

**404より悪い。** 404なら「無い」と分かるが、200で偽の同一性を返すと
**消費者は正しい答えを得たと信じる。**

### 裁定

**(1) 導出を1本にする。** 応答の `id` は**クエリに使うのと同じ規則**で
組み立てる。`sparql_iri` から角括弧を外した文字列を返す関数を切り出し、
**クエリ側と応答側の両方がそれを通る**形にする。
**裁定B59で `_id_path` を1本にしたのと同じ処置を、1フィールド隣に適用する。**

**(2) `id_path` はその正しい `id` から導出する**(`_id_path` は既に1本なので、
入力が正しくなれば自動的に正しくなる)。

**(3) `sparql_iri` のdocstringの偽の主張を直す。**
「素通りするだけで実質的に変化しない」は誤り。
**「Starletteがデコードした文字を再エンコードして戻すため、
どの入り方でも同じIRIに収束する」が正確**であり、
**だからこそ素の文字列連結と分岐する**ことを書く。

**(4) テストは実データのIRI形を使う。** fixtureのIRIがASCIIだけなら
この欠陥は原理的に出ない。**`%` を含むIRIを持つエンティティを
fixtureに入れること**(実データに8,555件あるので、代表を1件入れれば足りる)。
**入れずに直すと、次に同じ欠陥が入っても検出できない。**

### この発見の教訓(統制として記録する)

**裁定B59の検証は `queries.py` の関数呼び出しで行い、ルートを通していなかった。**
B59自身が「**アプリ層で検査すること**」を要求し、実装者はfixtureに対して
それを満たしたが、**controllerの実データ検証は関数レベルで止まっていた。**

**実データ × 実HTTPサーフェス の組み合わせだけが、この欠陥を出せる:**

| 検証の組み合わせ | この欠陥を検出できるか |
|---|---|
| fixture × 関数呼び出し | できない(fixtureのIRIがASCII) |
| fixture × HTTPルート | できない(同上) |
| **実データ × 関数呼び出し** | **できない**(`id_path` を自分で剥がして渡すため) |
| **実データ × HTTPルート** | **できる** ← ここだけ |

**「実データに当てた」だけでは足りず、「実データを、利用者と同じ入り口から
当てる」必要がある。** 欠陥型9(実データに一度も当てていない層は緑でも未検証)を
**「利用者と同じ入り口から当てる」まで強める。**

### 裁定B69の(4)と検証表の訂正(controllerの自己訂正。公開前に捕まえた)

**B69の初稿は「fixtureのIRIがASCIIだけならこの欠陥は原理的に出ない。
`%` を含むIRIをfixtureに入れること」と書いた。誤りである。**

`tests/phase1_fixture.py` を `grep "%"` して0件だったことから推論したが、
**fixtureはIRIを `src/jgkg/uris.py` 経由で組み立てる**:

```python
# src/jgkg/uris.py:59
return f"{_base()}/id/unresolved/jurisdiction/{quote(law_id, safe='')}/{quote(name, safe='')}"
```

fixtureの名称定数は**非ASCII**である:

```
OLD_KOUSEISHO_NAME = "厚生省"      -> %E5%8E%9A%E7%94%9F%E7%9C%81
NO_CANDIDATE_NAME  = "ダミー機関"  -> %E3%83%80%E3%83%9F%E3%83%BC%E6%A9%9F%E9%96%A2
```

**したがってfixtureの実行時グラフは `%` を含むIRIを持っている。**
**この欠陥はfixtureで検出可能であり、検出する検査が書かれていなかっただけである。**

### 検証表の訂正

初稿の表は「実データ × HTTPルート だけが検出できる」と書いたが誤り。
**正しくは、両方のモードで検出可能で、症状が違う**:

| 呼び方 | 渡す `id_path` | 症状 |
|---|---|---|
| 関数呼び出し | `SearchHit.id_path`(エンコード形) | `sparql_iri` が二重エンコードして **0件 → `None`(404)** |
| HTTPルート | 同じ値 | Starletteが1回デコードするので**当たるが、応答の `id` が偽** |

**どちらもfixtureで再現する。**

### では、なぜ誰も捕まえなかったのか(B59と同じ根本原因)

**既存テストはすべて `id_path` を手書きしている** ——
`"org/0000000000000"`・`PROJECT_CORE_ID` のような**ASCIIだけの値**である。
**裁定B59とまったく同じ根本原因**: **他方のエンドポイントの出力を使わず、
入力を手書きしている。**

実装者が追加した合成テストは `/search` の出力を使っており正しいが、
**`/search` が返す型(`_SEARCHABLE_TYPES`)に `UnresolvedReference` は
入っていない**ため、エンコードが必要なIRIがそのテストを通らない。

**欠けている検査は「関係の相手側からの1ホップ」である**:

**`related` が `id_path` を持つこと**は検査したが、

### 裁定の差し替え

**(4') fixtureにデータを足す必要は無い。**
**`%` を含むIRIを持つ既存のエンティティ(`UnresolvedReference`)に対して、
「関係の相手側から1ホップして `id` が一致する」検査を書く。**
**現行コードに対して先に書いて、落ちるところを見せること。**
