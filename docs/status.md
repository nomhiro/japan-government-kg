### 満たしていないもの(4件)

**いずれもコードとテストは存在するが、実行系を一度も動かしていない。**

| 条件 | 状態 |
|---|---|
| `scripts/build.sh <日付>` が成果物(`tdb2.tar.gz` + `manifest.json`)を生成する | ❌ 未実行 |
| manifestに Jenaバージョン・sha256・グラフ一覧・ソースごとの取得日が記録される | ❌ 実物の manifest が存在しない |
| `docker compose up fuseki` で成果物を読み取り専用で提供できる | ❌ 未実行 |

**理由**: 実装を委任したサブエージェントに、**ネットワークアクセスとDockerの実行を禁止した**。
安全側の判断だったが、その結果これら4件は手つかずである。
`data/` には手作りの参照表しかなく、**レイクにスナップショットは1件も無い。**

### 実測して記録すること(3件)— すべて未取得

計画Aは「推測値を先に置かない」ため、以下を実測して記録すると決めていた。**どれも数字が無い。**

- **TDB2インデックスの実サイズ**と1件あたりのトリプル数・バイト数
  — 全法人(約500万件)へ外挿してコンテナ環境のディスク上限に収まるか判断する根拠。**これが無いと Phase 1 の構成を決められない**
- **府省の突合率**(`ministries / (ministries + unmatched)`)
- **パイプライン全体とインデックス構築の実行時間**

### 残りは2種類ある(混ぜないこと)

- **経路が一度も通っていない**(条件6〜9)
  → **小さなサンプルでも通せる。** Docker があれば今すぐ着手できる。
  「動くと思っているが確かめていない」状態であり、**最も優先度が高い**
- **数字が無い**(実測3件)
  → **本物のデータが必要。** 法人番号の全件ダウンロード(約1GB)が前提

## 直せていない既知の問題

**「直した」と書けないもの。** 詳細は `docs/phase0-implementation-record.md`。

- **全件CSVの列位置が一次資料と照合されていない。** 「列がずれたら0件ではなく例外にする」までは実装済み
  (`src/jgkg/transform/organization.py` 冒頭に必須手順を記載)。**実データ投入前に一次資料と突き合わせること**
- **住所列だけの入れ替わりは検出できない。** 都道府県名の集合をコードに持つ判断が必要
- **`apache/jena-fuseki` のタグ命名が未検証**(ネットワーク禁止のため)。存在しなければ digest 指定などに変える
- **成果物差し替えのアトミック性が未実装**(symlink / blue-green)。前世代1つの退避のみ
- **隔離されたソースの出典記述が `kg.nq` に残る。** `--allow-partial` で出荷したKGは、SPARQLで問えば
  隔離済みソースについて「この日付に生成された」と答える(manifest 側は修正済み)
- **`MIN_ACCEPT_RATIO` は 50% のまま。** 実データの棄却率を見て決め直す判断が必要

## 次にやると効くこと(優先順)

1. **実行系を一度通す** — `build.sh` → `docker compose up fuseki` → SPARQLで引く。
   小さなサンプルで構わない。**「動くと思っているが確かめていない」を消す**
2. **実データを1回取得して3つの数字を測る** — TDB2実サイズ、府省突合率、実行時間。
   Phase 1 の構成判断がこれに依存している
3. **オントロジーの静的配信** — 語彙URIはハッシュURI(`#Agent`)なのでフラグメントはサーバに
   送られず、`/def/core` を返すだけで解決する。生成済みOWL/SHACLは静的ファイルで正準化済みなので、
   **トリプルストア無しで dereferenceable な LOD になる。**SPARQLエンドポイントより先に公開できる
4. **計画B(Phase 1)を書く**
