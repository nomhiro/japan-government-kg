# 継続収集の運用設計

作成日: 2026-10-04。利用者の「順番に整備して」を受けた収集管理の設計。
データ層の既存設計§6.1を引き継ぐ。政府全活動の網羅を保証する仕様ではない。

## 正本と責務

収集契約の正本は `src/jgkg/collection_registry.json`。型と検証、閲覧CLIは
`src/jgkg/collection.py`。17の収集単位を実装順に登録する。
この台帳には未実装・規約未確認の候補も含める。

`sources.py` はKGに実際に記録する出典と確認済み利用条件の正本として残す。
収集台帳は `source_id` で参照し、規約名・出典表示を複製しない。
候補を台帳に追加しただけでは、出典登録・コネクタ実装・KG収録は完了しない。
同じ提供元でも一覧・詳細・添付の完全性は別々に測る。
RS詳細には一覧とは別の出典IDを実装時に登録し、B117の一覧スナップショットを
詳細取得済みと読み替えない。

台帳ファイルはPythonパッケージ内に置く。作業ディレクトリによらずCLIから読める。
JSONからの検証で未定義項目、空台帳、重複ID、未知の出典参照を拒否する。
ブラウザ向けAPI・公開URI・オントロジーには台帳の内部IDを流用しない。

## 収集経路

1. 発見: 公式一覧・API・RSSから対象IDと資料URLを列挙する。
2. 取得: 公式URLから取得し、原本と取得日時、最終URL、HTTP状態、形式、ハッシュを保存する。
3. 抽出: 保存した原本を入力に処理する。原本をネットワークから取り直さず再処理できるようにする。
4. 照合: 権威あるIDを優先し、未照合と曖昧な一致を残す。
5. KG生成: 出典・取得日・根拠位置を持つ事実を名前付きグラフへ出力し、検証後に置換する。

発見・取得・抽出・照合・KG検証の成否を別々に記録する。
取得が成功しても抽出に失敗した文書を捨てず、再処理待ちにする。
一覧1ページや詳細1件の成功で全件成功を記録しない。

## HTTPと再開

- ソースごとに直列取得を基本とする。最初の実測は2秒以上の間隔を置く。
  これはプロジェクトの初期設定で、上流が保証した許容量ではない。
- 接続先の規約・robots・APIガイドを確認し、公式の上限があれば優先する。
- タイムアウトを設定し、429と一時的な5xxではRetry-Afterを尊重する。
  上限付き再試行とバックオフを使い、認証エラーや形式不一致を無限再試行しない。
- ページのnextや添付URLは許可したホスト・HTTPS・対象範囲を検査する。
  別府省・外部添付は明示的な許可先として登録する。
- HTTP 200だけで成功とせず、JSON/XML/PDF/ZIPの形式と必須項目を確認する。
- チェックポイントは対象IDと原本ハッシュで管理する。既存ファイルのハッシュを
  確認してから再利用し、壊れた原本を取得済みとしてスキップしない。
- 一時ファイルから原子的に保存し、部分取得の実行履歴を完了履歴と分ける。
- 全件走査中に上流が変わる場合は開始・終了の件数とID集合を比較し、収束しない
  実行を不完全として残す。件数の一致だけでは同じ集合と判定しない。

## 更新・削除

台帳の `check_interval_days` は取得確認の間隔案であり、上流の更新周期や
既存 `freshness.py` の鮮度基準とは意味が異なる。定期実行はまだ設定しない。

更新検知にはETag、Last-Modified、更新日時、原本ハッシュを使う。
RSSは発見の補助であり、全件一覧との定期照合を省略しない。
直近期間を重複取得して公開遅延を拾い、過去期間も周期的に再照合する。

一覧から消えた項目を即座に削除済みとしない。一覧走査の完了を確認したうえで
再確認し、非公開化・取消・移転・期限切れと取得障害を区別する。
KGの更新は対象グラフの置換で行う。部分走査で全件グラフを置換しない。
原本の保持期間・アクセス制御・再配布条件は公開元と資料種別ごとに決める。

## 完全性と実行記録

実装する各収集器は `data/collection-runs/<collection_id>/<run_id>/` に履歴を保存する。
日時はタイムゾーン付きUTC、run_idは衝突しない識別子とする。認証情報は記録しない。
原本は既存lakeを利用し、ソースID・取得日・ファイル名・ハッシュで履歴と接続する。
既存の日付単位lakeで同日再取得を保存する場合はrun_idをファイル名に含める。

履歴には次を含める。履歴保存・集計の実装は次段で行う。

| 項目 | 意味 |
|---|---|
| collection_id / source_id / contract_sha256 | 使用した収集契約と出典 |
| started_at / finished_at / scope | 実行期間と年度・院・機関・日付などの対象範囲 |
| discovery_complete / expected_count | 列挙が完了したか、公式一覧の対象件数。不明はnull |
| discovered_count / fetched_count / failed_count | 発見した対象、取得成功、取得失敗の一意件数 |
| not_public_count / not_yet_published_count | 非公開と未公表。取得失敗と区別 |
| extracted_count / linked_count / graph_validated | 抽出・照合・KG検証の結果 |
| snapshots / errors / checkpoint | 原本参照、失敗した対象と理由、再開位置 |

未知の分母を0で埋めず、全政府活動に対する収録率を算出しない。
最新試行と最後の完全成功を分けて表示する。単一ファイルのlake.latestだけで
複数ページ・添付を持つ収集単位の成功を判定しない。

## 実装順と完了条件

1. RS: 全年度一覧・年度選択、一覧全ページ、詳細全UUID、支出関連別APIを順に確認。
2. 国会: 会議・発言APIの日付分割、再開、件数照合。
3. 質問主意書: 両院の回次一覧、質問・答弁・経過を別管理。
4. 閣議: 年別一覧、案件、遅れて公開される議事録と決定本文。
5. パブコメ: 全状態の一覧、案件、添付、RSSとの照合。
6. 人物、審議会、調達、官報、裁判例、統計、政策評価、文書、公文書の順で拡張。
7. 既存の法令・RS CSV・法人番号も同じ実行記録へ接続する。

府省ごとに異なるHTML/PDF経路は、上位の分野エントリーから機関別の収集契約に
分割してから実装する。厚労省の入口だけで審議会全府省対応としない。

各収集器の完了条件は、公式取得条件確認、原本保存、再開、実測件数照合、
訂正・未公表・形式不一致の処理、履歴への接続。KGへの変換には対象オントロジーと
実データの検証を追加する。台帳整備とこれらの実装完了は区別する。
