# 日本政府ナレッジグラフ 設計書(Phase 0 + Phase 1)

- 日付: 2026-08-22
- 対象範囲: **Phase 0(基盤)と Phase 1(両ドメイン骨格+接続スライス)のみ**。Phase 2以降は§12のロードマップとして参照するだけで、本書の設計対象ではない
- 前提資料: `docs/2026-08-22-requirements-draft.md`(要求v0.2)、`docs/research/` 配下の調査3本

---

## 1. 目的と成功条件

### 1.1 何を作るか

日本政府が公開する資料・データを、統一オントロジーに基づくナレッジグラフ(KG)として統合し、政府情報の「つながり」を検索起点で辿れるようにする。データレイヤーと可視化アプリの2層セットで、コード・スキーマ・データをOSSライセンスで公開する公共財として構築する。

### 1.2 Phase 1の成功条件(受け入れ基準)

以下が可視化アプリ上で成立することをもって Phase 1 完了とする。

**縦の接続スライス(完了条件)**: 府省令・規則(法令番号に府省名を含む法令)から出発して、`法令 → 所管府省 → その府省の予算事業 → 事業の支出先法人` を画面遷移だけで辿れ、逆方向(法人 → 受けた事業 → 所管府省 → その府省の法令)も辿れる。各ホップに出典(一次資料URL・取得日時)が表示される。

**精度目標(完了条件に含めない)**: 法律については、行政事業レビューの根拠法令欄から解決できた分だけ `法律 → 予算事業` の直結エッジを張る。解決率を計測して公開するが、達成度を完了条件にはしない。

完了条件を府省令経由に置く理由は§7.2で述べる(法令APIに所管フィールドが存在しないことを実測で確認したため、確実に導出できる経路を完了条件に据えた)。この1本が通ることを最優先とし、各ドメインの網羅性は Phase 2 に譲る。「薄く広く作ってどちらのドメインも使えない」という失敗を、この単一の縦スライスを完了定義にすることで防ぐ。

### 1.3 Phase 1 で作らないもの

国会審議・パブコメ・官報・裁判例・EDINET・調達日次収集・人物(議員/幹部)レイヤー・統計指標・地理空間・PDF からの LLM 抽出・自然言語質問(GraphRAG)・SPARQL の一般公開。いずれも Phase 2 以降。

## 2. 設計原則(要求v0.2から継承、実装判断の拠り所)

1. **アプリファースト**: KGは内部表現。公開面は可視化アプリ。SPARQLエンドポイントの一般公開は看板アプリ稼働後に行う
2. **URI/ID設計を最優先で固定**: 後から変更できない唯一の要素として Phase 0 で確定する
3. **定常パイプラインの副産物としてKGを維持**: 収集は最初からスケジュール実行を前提に作る。手動実行専用のスクリプトを作らない
4. **政府の公式XML/APIを一次ソースに**: 政府側のRDF提供に依存しない
5. **標準への準拠と外部ハブへのリンク**: GIF/IMIコア語彙・DCAT・ELI参考の法令モデル・Wikidata sameAs
6. **全エッジに出典**: 出典を持たない事実をKGに入れない

## 3. 上位オントロジー(6軸・イベント中心)

政府データの関連性は「法令・組織・人・資金・政策」に収まらないため、上位構造を次の6軸で持ち、ドメイン追加時に上位構造を変えない設計とする。

| 軸 | 基底クラス(core) | Phase 1で使う範囲 |
|---|---|---|
| 誰が | `Agent`(組織・人の上位) | 府省・法人 |
| 何を | `Work`(法令・政策・事業・文書・判断の上位) | 法令・予算事業 |
| どこで | `Place` | 使わない(クラスのみ定義) |
| いつ | `Event`(時点を持つ出来事) | 公布・施行・改正・支出 |
| いくらで | `MonetaryItem` | 予算科目・支出 |
| 何について | `Concept`(SKOS準拠の主題・指標) | 使わない(クラスのみ定義) |

**イベント中心設計**: 「AがBに影響した」を直接のエッジにせず、原則として `Event` ノードを介す。理由は政府データのほぼ全ての関係が「いつの時点で真か」を持つため。例えば支出は `Expenditure`(事業・法人・金額・年度を持つEvent)として実体化し、`事業 --支出--> 法人` という時点情報を失うエッジは作らない。

**時点管理**: 法令は ELI の Work/Expression 二層に倣い、時点非依存の「法令そのもの」と「特定時点の版」を別リソースとして持つ。組織・事業の年度またぎの同一性は Phase 2 の課題として明示的に先送りする(§11.3)。

## 4. 識別子とURI設計(Phase 0 で確定、以後不変)

### 4.1 正準ID

| エンティティ | 正準ID | 一次ソース |
|---|---|---|
| 組織(府省・法人) | 法人番号(13桁) | 国税庁法人番号公表サイト |
| 法令 | e-Gov法令ID | e-Gov法令API v2 |
| 予算事業 | RSシステムの事業ID | 行政事業レビュー見える化サイト |
| 予算科目 | 年度+科目コード階層 | 財務省予算書XML |

府省も法人番号を持つため、行政機関と民間法人を `/id/org/` に統一する。府省コード(GIFコードリスト)は識別子プロパティとして保持し、コードからの逆引きを可能にする。局・課などの内部組織は法人番号を持たないため Phase 1 の対象外とする。

### 4.2 URIパターン

ベースURI は設定値 `JGKG_BASE_URI` として1箇所に集約し、全コードがこれを参照する。**構造は本書で確定し、以後変更しない。**

```
{base}/id/org/{法人番号}                     組織(府省・法人)
{base}/id/law/{法令ID}                       法令(時点非依存)
{base}/id/law/{法令ID}/{YYYYMMDD}            法令の時点版
{base}/id/project/{事業ID}                   予算事業
{base}/id/budgetitem/{年度}/{科目コード}      予算科目
{base}/id/expenditure/{事業ID}/{年度}/{連番}  支出(Event)
{base}/id/event/{種別}/{キー}                 その他のEvent
{base}/graph/{ソースID}/{取得日}              名前付きグラフ(出典単位)
{base}/def/{モジュール}#{用語}                オントロジー用語
```

**制約**: ベースURI のドメインが確定するまで、KGを外部に公開しない。ドメイン確定時の差し替えは設定1箇所のみで完結させ、それ以外の場所にドメイン文字列を書かない(CIで検出する)。

### 4.3 外部リンク

`owl:sameAs` / `skos:exactMatch` で Wikidata(法令は P8610、府省・法人はエンティティ)、統計LODの地域URI へリンクする。リンクは「あれば張る」扱いで、欠落を異常としない。

## 5. オントロジー管理

### 5.1 LinkML を単一のソース・オブ・トゥルース

`schema/*.yaml`(LinkML)を Git 管理し、CI で以下を生成する。生成物はコミットせず、ビルド時に作る。

- OWL/TTL — オントロジー本体(KGに同梱)
- SHACL — ロード前検証に使用
- Pydantic モデル — パイプラインとAPI層の型定義に使用
- JSON Schema / ドキュメント — 参照用

同一定義から RDF 側とアプリ側の型が生成されるため、スキーマ変更が両方に伝播する。これが案A(RDF中心)を選んでもアプリ開発の型安全を失わない根拠である。

### 5.2 モジュール構成

| モジュール | 内容 | Phase |
|---|---|---|
| `core` | 6軸の基底クラス、`Event`、provenance 用語 | 0 |
| `org` | 組織・府省・法人 | 0 |
| `law` | 法令、法令の時点版、改正関係、所管関係 | 1 |
| `budget` | 予算科目、予算事業、支出 | 1 |

Phase 2 以降は `person` / `document` / `statistics` / `judicial` / `place` をモジュール追加で足す。既存モジュールの破壊的変更を伴う場合はスキーマのバージョンを上げ、移行手順を記録する。

### 5.3 参照する外部語彙

GIF/IMIコア語彙(人・組織・場所・イベントの構造を参照。ただし IMI の存廃に依存しないよう、必要な定義は自モジュールに写して `skos:closeMatch` で対応付ける)、DCAT(データセット記述)、PROV-O(出典)、SKOS(主題)、ELI・Akoma Ntoso(法令構造の参考。準拠ではなく参照)。

## 6. アーキテクチャ

### 6.1 コンポーネント分割

各コンポーネントは単一の責務を持ち、ファイルベースの中間成果物で疎結合に連結する。上流の失敗が下流を巻き込まないこと、任意の段から再実行できることを設計目標とする。

```
[1] コネクタ層      ソース別に「取得してそのまま保存する」だけ
        ↓ 生ファイル(取得時のバイト列 + 取得メタデータ)
[2] データレイク    取得時点のスナップショットを不変で保持
        ↓
[3] 抽出・変換層    ソース別パーサ → 中間表現(Pydanticモデル)
        ↓
[4] エンティティ解決 中間表現の参照文字列 → 正準ID
        ↓
[5] RDF生成         中間表現 → RDF(名前付きグラフ単位)
        ↓ SHACL検証ゲート(不合格は隔離してロードしない)
[6] トリプルストア   Fuseki(名前付きグラフで出典を分離)
        ↓
[7] API層           SPARQL を隠蔽し、用途別のJSONを返す
        ↓
[8] 可視化アプリ    検索起点のSPA
```

**コンポーネント境界の理由**: [1]を「取得だけ」に限定するのは、パースの失敗と取得の失敗を分離し、パーサ修正時に再取得を不要にするため。[2]の不変スナップショットは、官報の90日制約(将来のPhase)と「過去の解釈を再現できること」の両方に効く。[4]を独立させるのは、名寄せの精度改善を他の層と無関係に反復できるようにするため。[7]でSPARQLを隠蔽するのは、アプリをストア実装から独立させ、将来のLPG投影やキャッシュ層の追加をアプリ改修なしに行えるようにするため。

### 6.2 技術選定

| レイヤ | 選定 | 理由 |
|---|---|---|
| パイプライン | Python(rdflib, pySHACL, LinkML, httpx) | LinkML・SHACL・RDFのツールチェーンがPythonに揃う |
| ストア | Apache Jena Fuseki(Docker) | OSS、Phase 1規模で十分、名前付きグラフとSPARQL 1.1に対応 |
| API層 | FastAPI | LinkML生成のPydanticモデルをそのまま応答型に使える |
| フロント | React + Vite + Sigma.js | Sigma.jsはWebGLで10万ノード級。検索起点UXに必要な規模を確保 |
| 実行環境 | docker-compose | どこでも動く。公共財としての再現性を優先 |

QLever への移行は「公開読取エンドポイントを出す段」で判断する。Fuseki と同じ SPARQL 1.1 で話すため、API層より下の差し替えで済む。

### 6.3 スケジュール実行

Phase 1 の更新頻度は月次(法人番号全件)・年次(予算・RS・法令は随時だが実質日次未満)であり、日次ジョブは不要。ただし**スケジューラを前提とした構造**(冪等な実行、前回取得との差分検出、失敗の記録と再実行)で作る。Phase 2 で日次ソース(調達・官報)が入ったときに構造を変えないため。

## 7. Phase 1 のデータソースと接続方式

### 7.1 使うソース(5つに限定)

| # | ソース | 取得 | Phase 1で取るもの |
|---|---|---|---|
| 1 | e-Gov法令API v2 | REST(登録不要) | 法令ID・法令番号(`law_num`, `law_num_type`)・法令名(`law_title`)・略称(`abbrev`)・分類(`category`)・公布日・改正関係(`amendment_*`)・廃止状態(`repeal_status`) |
| 2 | 行政事業レビュー(RSシステム) | バルクCSV | 事業ID・事業名・所管府省・予算額・**根拠法令(自由記述)**・**支出先(法人名・法人番号)** |
| 3 | 財務省予算書XML | バルクDL | 所管-組織-項-目の科目階層と金額 |
| 4 | 国税庁法人番号公表サイト | 全件CSV(月次) | 法人番号・商号・所在地 |
| 5 | GIFコードリスト | ファイル | 府省コード |

いずれも政府標準利用規約準拠(商用・再配布可)であり、非商用制約のあるソース(国土数値情報等)は Phase 1 に含めない。

### 7.2 縦スライスの接続点

#### 実測で判明した制約(2026-08-22)

`https://laws.e-gov.go.jp/api/2/laws` の実レスポンスを確認した結果、**法令API v2 に所管省庁を示すフィールドは存在しない**。取得できるのは `law_info`(law_type, law_id, law_num, law_num_era/year/type/num, promulgation_date)と `revision_info`(law_title, law_title_kana, abbrev, category, amendment_*, repeal_status, repeal_date, remain_in_force, mission 等)であり、`mission` は "New" のような改正種別を表す値で所管とは無関係、`category` は事項別分類である。

したがって「法令の所管府省」は API から直接取れない。この制約を前提に、接続を2経路で設計する。

#### 経路1: 法令番号からの府省導出(決定的・完了条件の土台)

府省令・規則の法令番号には府省名が含まれる(例「令和七年厚生労働省令第十号」)。`law_num` と `law_num_type` から府省名を抽出し、府省コード/法人番号へ決定的に解決する。現行法令のうち法律は一部で、政令・府省令・規則が多数を占めるため、この経路だけで相当数の法令に所管が付く。

法律・政令(法令番号に府省名を含まない)はこの経路では所管が付かない。欠落として扱い、経路2で補う。

#### 経路2: 根拠法令欄からの解決(精度目標)

行政事業レビューシートの様式には根拠法令欄があり、ここから法令への直結エッジを作る。解決は法令名(`law_title`)と**略称(`abbrev`)**での照合による。条・項レベルの解決は Phase 2 に送り、Phase 1 は法令単位までとする(これにより難度を大きく下げる)。

**未検証の前提**: RSシステムのCSVに根拠法令の列が含まれるかは実データで未確認(サイトがSPAのため静的取得では確認できず)。Phase 0 の先頭で実データを取得して検証し、結果で分岐する(§7.3)。

#### 接続点ごとの確度

```
法令(府省令・規則) ──[経路1: 法令番号]──→ 府省 ──所管──→ 予算事業 ──支出──→ 法人
法令(法律・政令)   ──[経路2: 根拠法令欄]──────────────────→ 予算事業
```

- **府省 → 事業**: RSのCSVに所管府省名があり、府省コード/法人番号へ決定的に解決。低リスク
- **事業 → 法人**: RSの支出先に法人番号がある行は決定的に接続。空欄・法人名のみの行が一定割合あることを前提とし、扱いを§8.2で定義
- **法令 → 府省**: 経路1で決定的(対象は府省令・規則)
- **法令 → 事業**: 経路2、解決率を計測

### 7.3 Phase 0 で先に検証すること

実装の順序として、以下を最初に実データで確認する。設計の前提が崩れた場合の分岐も定めておく。

| # | 検証項目 | 前提が崩れた場合 |
|---|---|---|
| 1 | RSのCSVに根拠法令の列があるか | 経路2を Phase 2 に送る。完了条件は経路1のみで達成できるため Phase 1 は継続 |
| 2 | RSのCSVに支出先の法人番号列があるか | 法人名のみでの名寄せに切り替え、解決率の目標を下げる。列自体が無ければ、支出先を Phase 2 に送り、完了条件を `法令 → 府省 → 事業` に短縮する |
| 3 | 法令番号から府省名を抽出できる法令の割合 | 極端に低い場合(想定外)、完了条件を経路2ベースに切り替える |
| 4 | 府省コードと府省の法人番号の対応表が入手できるか | 府省コードのみを識別子とし、府省だけ `/id/gov/{府省コード}` を使う例外を認める(§4.1の統一方針を1点だけ緩める) |

いずれの分岐でも「縦スライス1本を完成させる」という Phase 1 の性格は変えない。短縮する場合も、短縮したことを完了報告に明記する。

## 8. エンティティ解決と品質の扱い

### 8.1 三段構成

1. **ID直結**: 法人番号・法令IDが与えられている場合はそのまま採用
2. **文字列 blocking**: 法人名の正規化(法人種別語の統一、旧字体・全半角、「株式会社」前後位置)→ 候補絞り込み
3. **判定**: 候補が一意なら採用。複数または0件なら**未解決として記録**

LLM 判定は Phase 1 では使わない(§7.1のソースは決定的解決の余地が大きく、LLM導入は評価コストに見合わない)。Phase 3 で非構造データが入る段で改めて導入を判断する。

### 8.2 未解決を「無かったこと」にしない

未解決の参照は、参照文字列を保持した `UnresolvedReference` として KG に残し、`解決済み/未解決` を API とアプリで区別して見せる。理由は、公共財として「政府データにこの曖昧さが存在する」こと自体が利用者にとって情報であり、沈黙させると出典に遡れないデータができるため。

**受け入れ基準に解決率を含める**: 支出先法人の解決率と根拠法令の解決率を計測し、パイプラインの出力として毎回記録する。目標値は最初の実測後に設定する(推測値を先に置かない)。

### 8.3 SHACL 検証ゲート

RDF生成の直後に SHACL 検証を通し、**不合格のグラフはストアにロードしない**。不合格分は隔離ディレクトリに出力し、違反内容を人が読める形で報告する。「一部が壊れていても入れてしまう」ことを許すと、公共財としての信頼性が最初に崩れるため、ここは厳格側に倒す。

### 8.4 出典(provenance)

**名前付きグラフ単位で出典を持つ**方式を採る。各グラフに PROV-O で「どのソースの、いつ取得したファイルから、どのパーサバージョンで生成したか」を記録する。

要求v0.2ではRDF-starを挙げていたが、名前付きグラフ+PROV-Oを主方式に変更する。理由は (a) Fuseki と SPARQL 1.1 で確実に動く、(b) 出典の単位が「ソース×取得日」であり、トリプル単位の注釈は Phase 1 では過剰、(c) ツール互換性が高い。トリプル単位の注釈が必要になった箇所のみ RDF-star を後から足す。

## 9. APIと可視化アプリ

### 9.1 APIの責務

SPARQL を外に出さず、用途別のエンドポイントを提供する。

| 用途 | 返すもの |
|---|---|
| 検索 | 型混在のエンティティ候補(名称・型・要約) |
| エンティティ詳細 | 属性 + 関係の一覧(型別にグループ化)+ 各関係の出典 |
| 近傍サブグラフ | 指定ノードから深さ1-2のノード/エッジ(件数上限つき) |
| パス探索 | 2エンティティ間の経路(法令↔法人など) |

各応答は LinkML 生成の Pydantic モデルで型付けする。件数上限を必ず持ち、無制限のグラフ取得を許さない(hairball 防止をAPI側で保証する)。

### 9.2 アプリのUX

検索ボックス起点。エンティティページ(型別レイアウト)→ 近傍サブグラフ展開 → パス探索。全体グラフの一括表示は実装しない。全表示要素に一次資料へのリンクと取得日時を出す。想定ユーザーを特定類型に絞らない決定に従い、専門用語を避けた表示名を用い、専門機能(生データのダウンロード等)は副次的な位置に置く。

グラフ描画は Sigma.js。Phase 1 の規模では性能問題は出ないが、Phase 2 以降の拡大を見込んで最初から WebGL 系を選ぶ。

## 10. テスト戦略

TDD で進める。各層の性質に応じてテストの形を変える。

| 対象 | 方式 |
|---|---|
| パーサ(法令XML・予算XML・CSV) | ゴールデンファイル方式。実データの小片を固定入力として、期待する中間表現と比較 |
| エンティティ解決 | 正解ペアの固定セットに対する解決率・誤解決の計測。誤解決は解決漏れより重い扱い |
| オントロジー | LinkML スキーマから生成した SHACL で、正例・反例の両方を検証 |
| RDF生成 | 生成トリプルのスナップショット比較 |
| API | 型検査 + 代表クエリの応答検証 |
| 縦スライス | **統合テスト: 固定の府省令から固定の法人まで、経路1でホップを辿って到達できることを自動検証**(§1.2の完了条件をテストとして表現する)。経路2は解決率の計測として別立て |
| フロント | コンポーネント単位 + 主要導線のE2E |

外部APIへの実アクセスはテストに含めない(記録した応答を用いる)。ネットワークに依存するテストは別枠の疎通確認として分離する。

## 11. 非機能要件・リスクと対処

### 11.1 非機能

- **再現性**: `docker-compose up` と1コマンドのパイプライン実行で、誰の環境でも同じKGが再構築できる。公共財として最重要
- **冪等性**: 同じ入力から何度実行しても同じ結果になる。中断からの再開が可能
- **観測性**: 各段の処理件数・失敗件数・解決率をパイプライン出力として記録する
- **規模**: Phase 1 は法人全件を入れても数千万トリプル規模。Fuseki の単一インスタンスで扱える

### 11.2 ライセンス対応

ソースごとの利用規約を機械可読メタデータとして KG に保持し、アプリ表示時に出典と規約を自動表示する。Phase 1 のソースはいずれも商用・再配布可(政府標準利用規約準拠、またはGIFコードリストのCC BY相当)だが、この仕組み自体を Phase 1 で作る(Phase 2 以降に制約付きソースが入るため、後付けにすると全面改修になる)。

公開ライセンスはコードとデータで分けて選定する(§13の残論点)。

### 11.3 リスクと対処

| リスク | 対処 |
|---|---|
| 法令APIに所管フィールドが無い(**実測で確定**) | 法令番号からの府省導出(経路1)を完了条件の土台に据える(§7.2) |
| 根拠法令欄の解決が難航、またはCSVに列が無い | 経路2は精度目標であり完了条件外。列が無ければ Phase 2 に送る(§7.3) |
| 支出先の法人番号が空欄 | 未解決として保持し、解決率を可視化(§8.2) |
| RSの事業IDが年度をまたいで変わる | Phase 1 は年度内で閉じる。年度またぎの同一性は Phase 2 の課題として明記 |
| 政府側のAPI仕様変更・廃止(RESAS APIの前例) | コネクタを薄く保ち、スナップショットを残すことで過去分の再処理を可能にする |
| ベースURIのドメイン未確定 | 設定1箇所に集約し、確定まで外部公開しない(§4.2) |
| 公共財としての持続性 | 再現性(11.1)を担保し、特定個人の運用に依存しない構成にする |
