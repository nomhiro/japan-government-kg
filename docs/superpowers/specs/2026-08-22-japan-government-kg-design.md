## 1. 目的と成功条件

### 1.1 何を作るか

日本政府が公開する資料・データを、統一オントロジーに基づくナレッジグラフ(KG)として統合し、政府情報の「つながり」を検索起点で辿れるようにする。データレイヤーと可視化アプリの2層セットで、コード・スキーマ・データをOSSライセンスで公開する公共財として構築する。

### 1.2 Phase 1の成功条件(受け入れ基準)

Phase 1 の完了条件は**3つあり、すべて満たす必要がある**。KGとオントロジーが本体であるという原則1に従い、アプリ上の体験だけを完了条件にしない。

**(A) オントロジーの妥当性**: §5.6 のコンピテンシー質問 CQ1〜CQ10 のすべてに、SPARQLクエリで答えられる。CQに答えられないオントロジーは、アプリが動いても不合格とする。

**(B) 縦の接続スライス**: 府省令・規則(法令番号に府省名を含む法令)から出発して、`法令 → 所管府省 → その府省の予算事業 → 事業の支出先法人` を画面遷移だけで辿れ、逆方向(法人 → 受けた事業 → 所管府省 → その府省の法令)も辿れる。各ホップに出典(一次資料URL・取得日時)が表示される。

**(C) 更新の一巡**: §6.4 の一巡(取得 → 差分検出 → グラフ置換 → 検証 → リリース切替 → 鮮度反映)を実データで最低1回通し、**2つ目のリリースを作れる**こと。初回構築しかできない状態は Phase 1 未完了とする。

**精度目標(完了条件に含めない)**: 法律については、行政事業レビューの根拠法令欄から解決できた分だけ `法律 → 予算事業` の直結エッジを張る。解決率を計測して公開するが、達成度を完了条件にはしない。

完了条件を府省令経由に置く理由は§7.2で述べる(法令APIに所管フィールドが存在しないことを実測で確認したため、確実に導出できる経路を完了条件に据えた)。この1本が通ることを最優先とし、各ドメインの網羅性は Phase 2 に譲る。「薄く広く作ってどちらのドメインも使えない」という失敗を、この単一の縦スライスを完了定義にすることで防ぐ。

### 1.3 Phase 1 で作らないもの

国会審議・パブコメ・官報・裁判例・EDINET・調達日次収集・人物(議員/幹部)レイヤー・統計指標・地理空間・PDF からの LLM 抽出・自然言語質問(GraphRAG)・SPARQL の一般公開。いずれも Phase 2 以降。

### 1.4 政府提供物との関係 — なぜこれを作るのか

政府はAPIを多数提供しており(e-Gov APIカタログ掲載38件)、公式MCPサーバーも2本ある(Jグランツ、行政手続棚卸)。したがって「政府が既に出しているのでは」という問いに答えられる必要がある。調査(2026-08-22)の結論は次のとおり。

**政府は結合キーを配っているが、結合済みグラフは誰にも渡していない。**

権威ある識別子は整備・公開されている — 法令ID/法令標準XML、法人番号、町字ID(アドレス・ベース・レジストリ)、氏名突合モデル(`kanjikana-model`)。しかし、**それらのキーで横断結合されたグラフは公開されていない**。政府提供物の到達点は「個別APIによる単一ソースの検索・取得」であり、ソース横断の結合・名寄せ・出典付きの関係には踏み込んでいない。

具体的な境界:

| 政府提供物でできること | できないこと |
|---|---|
| 法令条文の検索・取得(法令API v2) | 法令 ↔ 予算・支出 ↔ 所管組織 の横断接続 |
| 統計表の取得(e-Stat API) | 統計指標と政策・予算事業の接続 |
| 住所の正規化(ABR + `abr-geocoder`) | 正規化した住所を軸にした横断結合 |
| 補助金・行政手続の自然言語検索(公式MCP 2本) | 「ある法令に基づく支出がどの法人にいくら流れたか」の追跡 |

**公式MCPの位置づけ**: 2本とも「技術検証を目的としたサンプルコード」と明示され無保証。対象はJグランツ(補助金)と行政手続棚卸調査で、**本設計の Phase 1 データソース5つのいずれもカバーしていない**。第三者製MCPは多数あるが star 100 超が1つもなく、依存先にできる成熟実装が存在しない。

**ガバメントAI「源内」との関係**: 政府は内部向けに、官報79年分・法令・白書・国会会議録・質問主意書を横断したAI活用データセットを整備し、全府省庁規模で実証している(2026-04にコードはOSS公開、データセット自体の外部提供は未確認)。これは**競合ではなく需要の証明**である — 政府自身がソース横断の統合を必要としている事実が本プロジェクトの方向性を裏付ける。一方で閉域網の職員向け環境であり外部から利用できない。ただし将来データセットが外部提供された場合は前提が変わるため、リスクとして監視する(§11.3)。

## 2. 設計原則(実装判断の拠り所)

1. **本体はオントロジーとKG。アプリはその検証装置**
   本システムの成果物はオントロジーとKGそのものであり、可視化アプリは「そのKGが実際に使えるか」を検証し、更新を続ける理由を作る装置である。先行事例調査で死んだのは *使われないエンドポイント* であり、生き残ったのは *更新が業務に埋め込まれたKG*(EU CELLAR・英legislation.gov.uk・統計LOD)だった。したがってアプリの存在は生存条件だが、**投資の中心はオントロジー設計と更新機構に置く**。UIの作り込みでオントロジーの粗さを覆わない。
2. **更新の一巡が回ることを初期からの要件にする**
   初期構築だけで完成する設計にしない。`取得 → 差分検出 → グラフ置換 → 検証 → 公開切替` の一巡を Phase 1 で通す(§6.4)。「一度作ってその後手で足す」構造を作らない。
3. **公開の順序としてはアプリを先に**(原則1の系)
   SPARQLエンドポイントの一般公開は看板アプリ稼働後に行う。利用者不在のエンドポイントを先に出さない。
4. **URI/ID設計を最優先で固定**: 後から変更できない唯一の要素として Phase 0 で確定する
5. **政府の公式XML/APIを一次ソースに**: 政府側のRDF提供に依存しない
6. **標準への準拠と外部ハブへのリンク**: GIF/IMIコア語彙・DCAT・ELI参考の法令モデル・Wikidata sameAs
7. **全エッジに出典**: 出典を持たない事実をKGに入れない

## 3. 上位オントロジー(6軸・イベント中心)

政府データの関連性は「法令・組織・人・資金・政策」に収まらないため、上位構造を次の6軸で持ち、ドメイン追加時に上位構造を変えない設計とする。

| 軸 | 基底クラス(core) | Phase 1で使う範囲 |
|---|---|---|
| 誰が | `Agent`(組織・人の上位) | 府省・法人 |
| 何を | `Work`(法令・政策・事業・文書・判断の上位) | 法令・予算事業 |
| どこで | `Place` | 使わない(クラスのみ定義) |
| いつ | `Event`(時点を持つ出来事) | 公布・施行・改正・支出 |
| いくらで | `MonetaryItem` | 予算科目・支出 |
| 何について | `Concept`(SKOS準拠の主題・指標) | 使わない(クラスのみ定義) |

**イベント中心設計**: 「AがBに影響した」を直接のエッジにせず、原則として `Event` ノードを介す。理由は政府データのほぼ全ての関係が「いつの時点で真か」を持つため。例えば支出は `Expenditure`(事業・法人・金額・年度を持つEvent)として実体化し、`事業 --支出--> 法人` という時点情報を失うエッジは作らない。

**時点管理**: 法令は ELI の Work/Expression 二層に倣い、時点非依存の「法令そのもの」と「特定時点の版」を別リソースとして持つ。組織・事業の年度またぎの同一性は Phase 2 の課題として明示的に先送りする(§11.3)。

## 4. 識別子とURI設計(Phase 0 で確定、以後不変)

### 4.1 正準ID

| エンティティ | 正準ID | 一次ソース |
|---|---|---|
| 組織(府省・法人) | 法人番号(13桁) | 国税庁法人番号公表サイト |
| 法令 | e-Gov法令ID | e-Gov法令API v2 |
| 予算事業 | RSシステムの事業ID | 行政事業レビュー見える化サイト |
| 予算科目 | 年度+科目コード階層 | 財務省予算書XML |

府省も法人番号を持つため、行政機関と民間法人を `/id/org/` に統一する。府省コード(GIFコードリスト)は識別子プロパティとして保持し、コードからの逆引きを可能にする。局・課などの内部組織は法人番号を持たないため Phase 1 の対象外とする。

### 4.2 URIパターン

ベースURI は設定値 `JGKG_BASE_URI` として1箇所に集約し、全コードがこれを参照する。**構造は本書で確定し、以後変更しない。**

```
{base}/id/org/{法人番号}                     組織(府省・法人)
{base}/id/law/{法令ID}                       法令(時点非依存)
{base}/id/law/{法令ID}/{YYYYMMDD}            法令の時点版
{base}/id/project/{事業ID}                   予算事業
{base}/id/budgetitem/{年度}/{科目コード}      予算科目
{base}/id/expenditure/{事業ID}/{年度}/{連番}  支出(Event)
{base}/id/event/{種別}/{キー}                 その他のEvent
{base}/graph/{ソースID}/{取得日}              名前付きグラフ(出典単位)
{base}/def/{モジュール}#{用語}                オントロジー用語
```

**制約**: ベースURI のドメインが確定するまで、KGを外部に公開しない。

> **この制約は当初「ドメイン文字列を設定1箇所以外に書かない」と書いていたが、事実として成立しなかった**(2026-08-22 全体レビューで判明)。ドメインは **`config.py` 以外に13箇所**存在した(`schema/*.yaml` 5・`schema/overlay/*.ttl` 1・`queries/cq/*.rq` 5、加えて `schema/generated/` の全生成物)。**そしてCIの検査は `src/**.py` の文字列grepしか見ていなかったため合格していた。** これは§5.7で戒めた「照合されない記録は記録の演技」と同型で、しかも本書自身の制約に対して起きた。
>
> **帰結が重い。** `.env` でドメインを差し替えると、データは新しい名前空間で書かれるのに**生成済みSHACLの `sh:targetClass` は旧名前空間のまま**になる。対象が1件も一致せず**全グラフが `conforms=True` になり、SHACL検証ゲートが素通しになる**(実測で確認)。ドメインは本書で唯一未決の項目なので、**この欠陥は必ず踏まれるものだった**。
>
> **正しい定式化**: ベースURIは**実行時の設定ではなく、生成時に焼き込まれるオントロジーの同一性**である。したがって制約は次の3つに置き換える。(1) 正は `config.py` の既定値とし、**差し替えは専用コマンドで全対象ファイルを一括書き換え + 再生成**とする。(2) `config.py` の既定値と全対象ファイル(**生成物を含む**)のドメインが一致しないなら**失敗する**検査を持つ。(3) **実行時にも、自オントロジーのクラスを名指ししているのに対応するシェイプが1つも無いなら例外にする** — これが無いと名前空間のずれが「対象0件で合格」に静かに退化する。

### 4.3 外部リンク

`owl:sameAs` / `skos:exactMatch` で Wikidata(法令は P8610、府省・法人はエンティティ)、統計LODの地域URI へリンクする。リンクは「あれば張る」扱いで、欠落を異常としない。

## 5. オントロジー管理

### 5.1 LinkML を単一のソース・オブ・トゥルース

`schema/*.yaml`(LinkML)を Git 管理し、CI で以下を生成する。

- OWL/TTL — 構造モデル(クラス・プロパティ・階層)
- SHACL — ロード前検証に使用
- Pydantic モデル — パイプラインとAPI層の型定義に使用
- JSON Schema / ドキュメント — 参照用

同一定義から RDF 側とアプリ側の型が生成されるため、スキーマ変更が両方に伝播する。これが案A(RDF中心)を選んでもアプリ開発の型安全を失わない根拠である。

**生成物は `.gitignore` に入れず、Git にコミットする。** 理由は3つある。(1) 差分レビューで生成器の回帰を検出できる、(2) 生成物の履歴が公開成果物の履歴になる、(3) **将来 LinkML を捨てる場合、最後の生成物をそのまま手書き管理に引き継げる** — これが LinkML 採用を可逆にする唯一の措置である(§5.3「撤退基準」)。

### 5.2 なぜ LinkML なのか — 代替案との比較

公共財として公開する設計であり、基盤選択の根拠を残す。調査(2026-08-22、`docs/research/2026-08-22-schema-tooling-comparison.md`)で以下を比較した。

| 案 | 評価 |
|---|---|
| **LinkML**(採用) | 1つの定義から OWL・SHACL・Pydantic・JSON Schema・ドキュメントが出る唯一の成熟した選択肢。**Gaia-X(EU連邦データ基盤)が本プロジェクトとほぼ同型の構成で本番運用中**(LinkML → SHACL + JSON-LD context + OWL、非生物医学、2026年も継続) |
| OWL/TTL と SHACL を手書き | 表現力は最大で依存もゼロ。しかし OWL・SHACL・Python型の3系統を人手で同期し続ける必要がある。**個人維持プロジェクトではこのドリフトが最大の死因**になる。欧州ELIはこの方式(手書き `eli.owl` + 別途SHACLバリデータ) |
| SHACL を単一のソース | SPDX 3.0(Linux Foundation)が採用し `shacl2code` で多言語バインディングを生成。しかし生成PythonがPydanticでなくFastAPIと摩擦し、**SHACL→OWLは原理的にロッシー**。`shacl2code` はメンテナ1名 |
| JSON-LD context + JSON Schema | JSON Schema は**グラフ形状制約を表現できない**(`sh:targetClass`、パス制約、`sh:qualifiedValueShape`)。RDFが主成果物のプロジェクトで検証能力を捨てることになる。採用しない |
| owlready2 | オントロジーを操作するライブラリで、SHACLもPydanticも生成しない。単一ソース戦略の代替ではない。かつ自前SQLiteクアッドストアを前提とし Fuseki 運用と競合。バス係数1 |

**当初の懸念2点は調査で解消・修正された。**

- *「イベント中心・関係実体化はLinkMLのレコード指向と噛み合わないのでは」* → **誤りだった。** LinkMLはメタモデルに `represents_relationship: true` と `relational_role`(SUBJECT/PREDICATE/OBJECT)を一級市民として持ち、関係の実体化は想定された用法である。`Event` を介した実体化は普通のクラスと普通のスロットで書ける
- *「公共部門はSHACLを規範形式にしているのでは」* → **半分正しい。** SHACLは規範的な *検証* アーティファクトだが、その上流ソースは機関ごとに異なる(SEMIC = UML/Enterprise Architect、SPDX = SHACL、ELI = 手書きOWL、ePO = UML/XMI)。**SEMICの方式は商用ツール依存で本プロジェクトには真似できない**。なお日本政府側(GIFはxlsx、IMIはRDFS)に規範形式の制約はなく、形式は自由に選べる

**OWL表現力の制約について**: LinkML公式は `gen-owl` の限界を自ら認めており(ruleの一部のみOWL化、`Any` レンジは OWL Full になる等)、さらに「LinkMLはスキーマモデリングのフレームワークであり、オントロジーモデリングのフレームワークではない」と明言している。ただし本設計では実行時への影響がない — Fuseki(既定構成)も QLever も**クエリ経路でOWL DL推論を回さず**、CQはSHACL検証済みデータに対するSPARQLテストである。またイベント中心設計は「時点情報を失う推論ショートカット」を意図的に拒否しているため、プロパティ連鎖(`owl:propertyChainAxiom`)を必要としない。残る影響は公開OWLの忠実度であり、§5.5 のオーバーレイで対処する。

### 5.3 撤退基準 — いつ LinkML を捨てるか

以下のいずれかに該当したら再評価する。生成物をコミットしているため、撤退は「生成を止め、最後の生成物を手書き管理に移し、YAMLを削除する」で完了する(移行コストの見積りは1〜3人週)。

- 必要な公理が LinkML でもオーバーレイでも表現できない
- `gen-shacl`(現在Beta)の制約により、**手書きSHACLとの混在**が避けられなくなった — 混在は両方の悪いところ取りであり、最も避けたい状態
- LinkML プロジェクトの維持が停止した(KuzuDB の前例に倣い、リリース・コミット頻度を定期確認する。現状は 1.11.1 / 2026-05-20、複数機関・複数資金源で健全)

**逆に、高価で不可逆な決定は LinkML ではない。** URI設計・出典モデル(名前付きグラフ+PROV-O)・6軸の概念的な切り方・ELIのWork/Expression二層の粒度 — これらは一度公開・投入すると巻き戻せない。検討予算はそちらに配分する。

### 5.4 モジュール構成

| モジュール | 内容 | Phase |
|---|---|---|
| `core` | 6軸の基底クラス、`Event`、provenance 用語 | 0 |
| `org` | 組織・府省・法人 | 0 |
| `law` | 法令、法令の時点版、改正関係、所管関係 | 1 |
| `budget` | 予算科目、予算事業、支出 | 1 |

Phase 2 以降は `person` / `document` / `statistics` / `judicial` / `place` をモジュール追加で足す。

### 5.5 公理オーバーレイ — LinkMLで書けない公理の置き場

LinkML の `gen-owl` が出せない公理(外部語彙への `owl:equivalentClass`、軸間の `owl:disjointWith`【→ **決定44で反証。直後の追記を参照** — `gen-owl`は`children_are_mutually_disjoint`で軸間の排他を出せる】、限定基数制限など)は、**加算専用の手書きTTLオーバーレイ** `schema/overlay/*.ttl` に置く。公開するオントロジーは「生成OWL + オーバーレイ」を CI でマージしたものとする【→ **決定44で反証。直後の追記を参照** — マージはしない。公開するのは生成OWLのモジュール別ファイルそのもの】。

>    直接の親クラスに立てると、直接の子クラス全体を1つの `owl:AllDisjointClasses`
>    (`owl:members` に子クラスのリスト)にまとめて出す(実測)。pairwiseの21本
>    ではなくn項公理1本だが、OWL 2 の `DisjointClasses(C1…Cn)` は「全ての i<j

> 2. **公開するオントロジーは生成OWLのモジュール別ファイルである。** `src/jgkg/site.py`
>    が配布するのはこれで、オーバーレイとのマージはしない。オーバーレイは
>    LinkMLで表現できないものが将来現れたときの逃げ道として残すが、**公開経路には

>    オーバーレイにしかなく、オーバーレイは公開経路に無かったため)。Task 12は

> `core` を import する5モジュール(`core`/`org`/`budget`/`law`/`all`)の生成OWL
> 全てに同じ排他公理が(別のBNodeとして)重複して現れる。冗長だが無害(冪等な公理・

> importする範囲内でしか直接の子クラスを集めないため、core以外の4モジュールでは

**なぜ上位オントロジーごと手書きに分離しないのか**: 分離すると、ドメインクラスが上位クラスを LinkML の `is_a` で継承できなくなり、全ドメインクラスの継承関係を手書きの `rdfs:subClassOf` に移す必要が生じる。オーバーレイ方式ならクラス階層は LinkML に残り、公理だけが外から加算される。唯一の参照事例である Gaia-X も上位を分離せず LinkML に統合している。

**オーバーレイの規約(ドリフト防止)**:
- **加算のみ**。生成OWLが述べたことを上書き・否定しない
- 言及するクラス・プロパティは**すべて生成OWLに存在すること**をCIで検証する(§10)【→ **最終レビュー要修正8で反証** — この検査(`test_overlay_terms_all_exist_in_generated_owl`)はTask 12で削除された。CIはlint/生成物一致/base_uri --check/pytestの4ステップで、オーバーレイ用語の存在検査は含まれない。代わりに`test_overlay_is_empty_pending_new_axioms`が「オーバーレイにトリプルを1つでも足したら落ちる」ことだけを主張し、そのエラーメッセージが「対応する整合テストを復活させること」と明示する形で危険を封じている】。存在しない用語への公理は、スキーマ側の未反映かタイポである
- オーバーレイが肥大化したら、それは LinkML の限界に達した徴候であり §5.3 の撤退基準を再評価する契機とする

### 5.7 オントロジー自体を公開成果物として扱う

オントロジーはアプリの内部実装ではなく、単独で参照・再利用される公開物である。したがって以下を Phase 0 の成果物に含める。

- **日本語の用語定義ドキュメント**: LinkML から生成し、各クラス・プロパティに定義と出典(参照した外部語彙)を記す。**LinkML の `description` は単一文字列で言語別に持てない**ため、日英併記は「日本語を `description`、英語を `structured_aliases` + `in_language: en`」という規約で行う(この規約は最初に決め、後から変えない)
- **定義文には言語タグ `@ja` を付ける。** 対象は定義文(`skos:definition` / `sh:description`)のみで、要素名である `rdfs:label` には付けない(`houjinBangou` のようなASCII識別子に日本語の印を付けるのは誤りになる)。
  > **実装上の注意(2026-08-22 実機で確認)**: `gen-owl` / `gen-shacl` の `--default-language` オプションは **`linkml==1.11.1` には存在しない**。linkml.io の現行ドキュメントには記載があるが、未リリースブランチのドキュメントが先行しているだけで、どのリリース版にも実装されていない。したがって言語タグは**生成後にrdflibで付ける後処理**で実現する。またLinkMLは説明文を `rdfs:comment` ではなく `skos:definition` に出力する。
- **生成は環境非依存にする。** Windowsではstdoutがコンソールのコードページ(cp932)で開かれ、リダイレクトしたTurtleが不正なUTF-8になる。生成スクリプトで `PYTHONUTF8=1` を設定し、どの環境でも同じ生成物になるようにする(§11.1の再現性要件)
- **生成物を正準化する。LinkMLの生成はそのままでは非決定的である。**
  > **実装上の注意(2026-08-22 実機で確認)**: `gen-owl` / `gen-shacl` は**入力を一切変えずに再実行するだけで出力が変わる。** 差分は改行や空白ではなく、OWL/SHACLのブランクノード(`owl:Restriction` / `sh:property`)の**出現順序そのもの**である。`gen-owl` を直接2回実行して128行差、`PYTHONHASHSEED=0` を付けても119行差を実測した。原因はPythonのハッシュランダム化ではなく、rdflibがブランクノードのラベルをプロセスごとにランダムに振ることにある。
  >
  > これを放置すると**上の§5.1「生成物をあえてコミットする」の目的(1)差分レビューで生成器の回帰を検出する、が成立しない**(毎回意味のない差分が出るためレビュー不能になる)。また§11.1の再現性要件にも反する。
  >
  > したがって**生成の最後に正準化を行う**。rdflibの正準化でブランクノードのラベルを内容から決定し、バイト単位で同一の出力を得る。**N-TriplesはTurtleの構文上の部分集合なので、行単位でソートしたN-Triplesを `.ttl` として書き出しても既存のパーサはすべて読める。** 可読性は落ちるが、**人間が読む正本はLinkMLのYAML**であり、生成物は差分レビューと再現性のために存在する。
  >
  > **検証は「3回連続実行してバイト単位で一致すること」で行う。** 2回では偶然の一致が残る。
- **バージョニング**: セマンティックバージョンを付す。後方互換な追加はマイナー、既存用語の意味変更・削除はメジャー。**URIは維持し、非推奨は `owl:deprecated` で表す(URIを消さない)**
- **変更履歴**: 変更の理由をCQへの参照とともに残す(「CQ11を追加したためクラスXを追加」)
- **公開形式**: OWL/TTL(生成OWLのモジュール別ファイル。オーバーレイとのマージはしない — §5.5決定44)と SHACL をリリース成果物として配布し、DCATで記述する
- **LinkML のバージョンをピン留めする**(例 `linkml==1.11.1`)。1.11.0 が誤ったコミットに紐づいてyankされた前例があり、生成物の再現性はツールのバージョン固定に依存する

## 6. アーキテクチャ

### 6.1 コンポーネント分割

各コンポーネントは単一の責務を持ち、ファイルベースの中間成果物で疎結合に連結する。上流の失敗が下流を巻き込まないこと、任意の段から再実行できることを設計目標とする。

```
[1] コネクタ層      ソース別に「取得してそのまま保存する」だけ
        ↓ 生ファイル(取得時のバイト列 + 取得メタデータ)
[2] データレイク    取得時点のスナップショットを不変で保持
        ↓
[3] 抽出・変換層    ソース別パーサ → 中間表現(Pydanticモデル)
        ↓
[4] エンティティ解決 中間表現の参照文字列 → 正準ID
        ↓
[5] RDF生成         中間表現 → RDF(名前付きグラフ単位)
        ↓ SHACL検証ゲート(不合格は隔離してロードしない)
[6] トリプルストア   Fuseki(名前付きグラフで出典を分離)
        ↓
[7] API層           SPARQL を隠蔽し、用途別のJSONを返す
        ↓
[8] 可視化アプリ    検索起点のSPA
```

**コンポーネント境界の理由**: [1]を「取得だけ」に限定するのは、パースの失敗と取得の失敗を分離し、パーサ修正時に再取得を不要にするため。[2]の不変スナップショットは、官報の90日制約(将来のPhase)と「過去の解釈を再現できること」の両方に効く。[4]を独立させるのは、名寄せの精度改善を他の層と無関係に反復できるようにするため。[7]でSPARQLを隠蔽するのは、アプリをストア実装から独立させ、将来のLPG投影やキャッシュ層の追加をアプリ改修なしに行えるようにするため。

### 6.2 技術選定

| レイヤ | 選定 | 理由 |
|---|---|---|
| パイプライン | Python(rdflib, pySHACL, LinkML, httpx) | LinkML・SHACL・RDFのツールチェーンがPythonに揃う |
| ストア | Apache Jena Fuseki (TDB2) | 名前付きグラフの成熟度が最高、成果物配布方式が上流公認、SHACLが同一スタック、Apache財団でバス係数が高い(§6.2.1) |
| API層 | FastAPI | LinkML生成のPydanticモデルをそのまま応答型に使える |
| フロント | React + Vite + Sigma.js | Sigma.jsはWebGLで10万ノード級。検索起点UXに必要な規模を確保 |
| 実行環境 | docker-compose | どこでも動く。公共財としての再現性を優先 |

#### 6.2.1 ストア選定の根拠(調査 `docs/research/2026-08-22-neptune-and-oss-rdf-stores.md`)

**Fuseki (TDB2) を採用する理由**:

1. **名前付きグラフの成熟度が最高。** 名前付きグラフは本設計の必須要件(出典管理の基盤)であり、Wikimedia財団のWDQS後継評価で Jena は quad対応 **5/5** の評価を得ている
2. **成果物配布方式が上流公認。** Jena公式ドキュメントが「読み取り専用データセットなら、ディスク上のDBをコピーして複数のFuseki+TDB2インスタンスに複製し、ロードバランサを前置する」構成を明示的に推奨している。**§6.3の方式は本プロジェクトの発明ではなく、上流が想定し文書化した使い方である**
3. **SHACL検証が同一スタックで完結する。** 検証を別ツールに分離する必要がない
4. **Apache財団プロジェクトで複数コミッタ。** 個人〜小規模開発が公共財を長期運用する前提では、エンジンの継続性が最大のリスク要因である(KuzuDBの前例)
5. 数千万トリプルは TDB2 の射程内で天井に遠い。天井が問題になるのは数十億規模

**QLever は「条件付きの将来オプション」に格下げする**(従来は移行を既定路線としていた)。理由:

QLever は魅力的である(ロード速度が候補中最速の1.7M triples/秒、インデックスサイズ最小、Apache-2.0、CIの透明性、そしてWikimedia財団がWDQSの後継として選定)。**しかしWMFの判断を本プロジェクトに転用してはならない。**

WMFの評価表では **QLever の名前付きグラフ対応は 0/5** であった。それでも選ばれたのは **WDQSが名前付きグラフを実質的に必要としていないから**である。その証拠が graph split の実装方式で、これは1つのインデックス内の複数の名前付きグラフではなく、**2つの独立したエンドポイント**として実現されている。QLever の名前付きグラフ対応は2024年12月にマージされたばかりで、**上流自身が「Gでソートされたpermutationが必要な場合はまだ効率的でない」と明記している**。

名前付きグラフが必須の本プロジェクトでは、これは必須要件に対する読めないリスクである。移行を検討する場合は以下のゲートを通す。

- **自分の実データと実クエリで、名前付きグラフを含むベンチマークを取る**(特に `GRAPH ?g { ... }` と複数グラフを跨ぐJOIN)。他人のベンチマークでは分からない
- WMFのFY27段階移行(2026年7月以降)の結果を観察する。**世界最大級のRDF運用による無料の battle-testing を活用する。**ただしWDQSは名前付きグラフを使わないため、quad関連の問題はWMFの運用では露出しない点に注意
- 移行は「エンジン差し替え」ではなく**並行エンドポイント**で行う。成果物配布方式なら容易(同じRDFから2種類の成果物を作るだけ)

なお本設計は SPARQL UPDATE を使わず「CIでインデックスを再構築して丸ごと差し替える」方式なので、**QLever の UPDATE が基本形のみという制約は問題にならない**。ここは相性が良い。

#### 6.2.3 規模が問題になったときの対処順序

**エンジン移行は最後の手段とする。** この順で試す。

1. **成果物とエンドポイントを分割する**(府省庁別・データセット別)。**Wikidataが最終的に恒久化した解**であり(graph splitは一時的な回避策ではなく恒久的なアーキテクチャ決定として維持されている)、既存設計の延長で実現でき、エンジン移行のリスクもクエリ破壊もない
2. **リードレプリカを増やす**(同じ成果物をN台に展開してロードバランサを前置)。読み取り中心のワークロードで効果が大きく、Jena公式が推奨する構成
3. **TDB2のチューニング**(JVMヒープを2〜4GBに抑えてOSページキャッシュを最大化する。TDB2はメモリマップ依存なのでヒープを大きくしても逆効果)
4. **それでも足りなければQLever**(上記ゲートを通してから)

**エンジン移行は「あとで変えればいい」では済まない。** WMFはWDQSのバックエンド移行にあたり、クエリ書き換え支援のためにcontractorを雇っている。エンジンを変えるとエンジン固有の挙動に依存した既存クエリが壊れ、**公共財として外部にエンドポイントを提供している場合、その破壊的変更のコストは利用者にも及ぶ**。

### 6.3 デプロイ方針 — データベースを「成果物」として扱う

調査(2026-08-22、`docs/research/2026-08-22-azure-rdf-hosting.md`)を踏まえ、**トリプルストアのインデックスを実行環境から切り離し、CIが生成する成果物(artifact)として扱う**。

```
CI: 取得済みスナップショット → RDF生成 → SHACL検証 → tdbloader2 でインデックス構築
      → tar.gz として公開(Blob / GHCR 等)= これがKGのリリース版(§6.4)
実行側: 起動時に成果物を取得してローカルディスクに展開し、読み取り専用で提供するだけ

**層の分離をリリースサイクルの独立として要件にする(2026-08-23 追加)。** 本設計は3つの層からなり、
それぞれが**独立にリリースできる**ことを構成の要件とする。

| 層 | 実体 | リリースの単位 |
|---|---|---|
| データ | TDB2インデックス(不変・版付き・manifest + sha256) | 取得日ごとの成果物 |
| ストア | Fuseki コンテナ(コードのみの小さいイメージ) | Jenaバージョン更新時のみ |
| アプリ | API + 静的フロントエンド | コード変更時 |

> この要件は当初から暗黙に成立していたが、明示されていなかったため
> 「インデックスをコンテナイメージに焼き込む」という**層を結合する提案が実際に出た**(撤回済み)。
> 焼き込みはAPIのバグ修正にGB級のイメージ再構築を要求し、データ更新にアプリの再デプロイを
> 要求し、ロールバックの粒度を失わせる。**独立に変わる流れを1つの成果物に押し込んではならない。**
> なお提案の根拠にされた「配布物と展開後が約1000倍違う」は37トリプルの固定オーバーヘッドの
> 反映であり、外挿には使えないと本書自身が記録していた数字である。

**フロントエンドの配信は Cloudflare Pages とする(確定)。** オントロジーの静的配信
(`/def/*`)と可視化アプリの静的アセットは Pages が担い、`jgkg.norr-tech.com` を玄関にする。
静的層はバックエンドの実測に依存しないため先行して確定・検証できる。
**API + Fuseki のホストは未確定のまま維持する** — 上記「Phase 1 で実測すること」の
TDB2実サイズが判断材料であり、実測なしに前提にしない。

> **実装上の注意(2026-08-23 実機で確認)**: ここでいう「読み取り専用」を**ファイルシステムで担保することはできない。**
> TDB2 は起動時にプロセスロックファイルを作るため、読み取り専用マウント上では**データベースを開けない。**
>
> ```
> java.nio.file.FileSystemException: /fuseki/databases/kg/tdb.lock: Read-only file system
> ```
>
> したがって成果物のディレクトリは書き込み可能でマウントし、**書き込み禁止は別の2つで担保する。**
> (1) Fuseki のアセンブラが公開するのは `fuseki:query` のみで、更新エンドポイントを持たない。
> (2) 成果物は content-addressed で、配置前に `serve.sh` が sha256 と Jenaバージョンを照合する。
> 差し替えは成果物の入れ替えでのみ行う。設定ファイル側は本当に読み取り専用にできるので `:ro` を維持する。
>
> **上の「上流公認」の主張は方式(DBをコピーして複製し前段に置く)についてであり、マウントを
> 読み取り専用にできるという主張ではない。** 当初の記述はそこを混同していた。
>
> **もう1点、規模の見積りに関わる実測**: 37トリプルのTDB2インデックスが **192 MiB**、
> その `tdb2.tar.gz` が **202 KB** だった。TDB2はノード表とインデックスを先に確保するため
> **データ量にほぼ依存しない固定オーバーヘッド(約192 MiB)がある**。確保済みの疎な領域は
> 圧縮でほぼ消えるため、**配布物と展開後のサイズが約1000倍違う。**
> したがって(a)小さいサンプルからの1件あたり単価の外挿は成立しない、
> (b)**コンテナ環境の一時ディスク上限は展開後のサイズで判断する必要がある**(配布物の
> サイズで判断してはならない)。全法人規模での実測は plan B で行う。
```

**この形を選ぶ理由(4つとも本設計の特性から導かれる)**:

1. **ステートフルなボリュームが不要になる。** サーバーレスコンテナ環境(Azure Container Apps 等)は永続ストレージがネットワークファイル共有しか無い場合があり、これは後述の理由でトリプルストアに向かない。成果物方式なら永続ボリュームの問題自体が消える
2. **一括ロードのCPU負荷を実行環境から追い出せる。** `tdbloader2` は数十分CPUを使い切る。バースト系VM(Azure B-series等)ではCPUクレジットを枯渇させ、ロード後もベースライン性能に絞られる。ロードはCI側でやるのが正しい
3. **§6.4のリリース版がそのまま実体になる。** 「KGのリリースをDCATで記述する」という設計が、抽象的な版番号ではなく**配布可能な1個のファイル**として実装される。再現性(§11.1)も自動的に満たされる
4. **可搬性が最大化する。** どのクラウドにもマネージドRDFの安価な選択肢が無いため(下記)、どこでも自前運用になる。成果物方式なら Azure・他クラウド・VPS のどこにでも同じものを載せられ、価格交渉力が保たれる

**更新は成果物の差し替えと再起動で完了する。** 名前付きグラフの置換(§6.4)はCI側のRDF生成段で行われ、実行側は新しいインデックスを受け取るだけになる。更新失敗時に前リリースが残る要件も、前の成果物を保持するだけで満たせる。

**この方式は上流公認である。** Jena公式ドキュメントが「読み取り専用データセットなら、ディスク上のDBをコピーして複数のFuseki+TDB2インスタンスに複製し、ロードバランサを前置する」構成を明示的に推奨している。本プロジェクトの発明ではなく、想定された使い方である。

#### 成果物の運用規約

Amazon Neptune が分散ストレージ層で得ている性質を、この方式は粗い粒度で得ている(Neptuneはページ単位で分離し分散ログで整合性を取る。本方式はインデックス全体の単位で月次に差し替える)。**読み取り中心・月次バッチ更新という本設計の要件では、この粗い粒度がむしろ正解である** — Neptuneが莫大な実装コストを払って解決している問題(書き込みのdurability、レプリカ間の一貫性)が本プロジェクトには存在しないためである。その上で、以下を規約として定める。

- **成果物を content-addressed にする**(ハッシュをファイル名かmanifestに含める)。Neptuneのsegment自動修復に相当する「壊れたデータを検出する」能力を、チェックサムで安価に得る
- **差し替えはアトミックに行う。** symlinkの切り替えか、新インスタンスを立ててからロードバランサを切り替える(blue/green)。**TDB2はメモリマップを使うため、稼働中のディレクトリを上書きしてはならない**
- **ロールバックを明示的に設計する。** 過去N世代の成果物を保持し、切り戻し手順を文書化・自動化する。前月の成果物を指定するだけで巻き戻せることは**Neptuneのスナップショット復元より軽量な、この方式の最大の強み**であり、暗黙にせず設計項目として扱う
- **Jenaのバージョンをmanifestに記録し、実行側で照合する。** TDB2のオンディスク形式はJenaのバージョンに紐づくため、ビルド側と実行側でバージョンがずれると読めなくなる恐れがある(一次情報で確認した仕様ではなく、予防措置)
- **CIで検証を通った成果物だけが本番に出る**という構造を強制する。SHACL検証(§8.3)とCQテスト(§10)のゲートがそのままリリースゲートになる

#### ストレージの前提 — ブロックデバイスが必要

**Jena TDB2 は 64bit Java 上でメモリマップドファイルを使う**(Jena公式ドキュメントの明記事項)。また Jena は **「複数のJVMが同じファイルデータベースを使う構成は非サポートであり、データ破損のリスクが高い」** と明記している。QLever も同様にディスク上のインデックスをmmap前提で読むため、この要件は QLever に替えても消えない。

したがって**インデックスはローカルのブロックデバイス上に置く**。ネットワークファイル共有(SMB/NFS)上に置く構成は避ける。

> 正確に言うと、Jena の公式ドキュメントに「NFS/SMB を使うな」という明文の禁止規定は無い。回避すべき根拠は (a) mmap はOSのページキャッシュ管理に依存し、ネットワークファイルシステムではコヒーレンシとflushの意味論が同等に保証されない、(b) 複数レプリカが同じファイル共有をマウントすると、Jenaが「非サポート・破損リスク高」と明記した状態そのものになる、(c) mmapのページフォルトが毎回ネットワーク往復になり性能が出ない、という3点である。**特に (b) は、レプリカ数が増えうるサーバーレスコンテナ環境で現実的な危険**であり、静かなデータ破損として現れうる。

**Phase 1 で実測すること**: 構築後のTDB2インデックスの実サイズ。サーバーレスコンテナ環境の一時ディスク上限(Azure Container Apps では最大8 GiB)に収まるかで、実行環境の選択肢が変わる。数千万トリプル規模では上限に近いと見込まれるため、実測なしに前提にしない。

#### クラウド選択について

**Azure にはマネージドのRDF/SPARQLサービスが存在しない**(2026年8月時点)。Microsoft自身のAWS対比表は Amazon Neptune の対応物を Cosmos DB(プロパティグラフ)としており、Microsoft Fabric の Graph は公式ドキュメントで **「RDFはサポートしない。セマンティックウェブ標準やオントロジーが必要なら、RDFをサポートする他のプラットフォームを検討せよ」** と明記している。

**ただしこれは案A(RDF中心)の判断を変えない。** 理由は、Azureでプロパティグラフに倒しても何も得しないためである。

- Cosmos DB for Apache Gremlin は**名前付きグラフの概念を持たない** — 本設計の出典管理(§8.4)が成立しなくなる。加えてトラバーサルのタイムアウト30秒・反復上限32ホップという制約があり、探索的クエリに向かない。さらに全ドキュメントに他サービスへの誘導バナーが付いており、新規採用を勧められていない
- Fabric Graph は上記のとおりRDF非サポートを公言している
- Neo4j に倒す場合、それはAzureのマネージドサービスではなく第三者SaaSであり、自前運用と運用負荷の構図は大差ない。RDF標準(名前付きグラフ・SHACL・SPARQL federation・W3C準拠という公共財としての価値)を捨てる代償だけが残る

**「Azureに寄せるためにRDFを捨てる」という取引は成立しない。** そしてどのクラウドにも安価なマネージドRDFが無い(AWS Neptuneは本物だが最安構成で月$68〜104、Serverlessは下限1 NCUでゼロにスケールせず月$117が床)ため、**特定クラウドにロックインする動機がそもそも無い**。クラウド非依存(docker-compose)を維持する現在の方針は、この状況では最適である。

**コストの目安(2026年8月時点の公開価格)**: Phase 1 の内部利用構成(VM 2vCPU/8GiB + ブロックディスク64GiB)で月$66程度(米国東部)/$85程度(東日本)。RDFダンプをオブジェクトストレージで配布するだけなら月$1〜2。**クエリ可能なエンドポイントを立てる差額は月$35〜70程度**であり、この額で意思決定できる。

**外向き通信量(egress)が最大のコスト要因になる**点に注意する。公開SPARQLはレスポンスサイズが予測できず、東日本で$0.12/GB、月1TBで約$108とVM代を超える。**§9.1のAPI層の件数上限は、性能対策であると同時にコスト対策である。**

### 6.4 継続的更新の機構(Phase 1 の必須要素)

KGは一度作って終わるものではなく、更新が止まった瞬間に価値を失う。したがって**更新機構は Phase 1 の必須要素**とし、後付けにしない。設計原則2に対応する。

#### 更新の一巡

```
取得 → 差分検出 → グラフ置換 → SHACL検証 → リリース版の切替 → 鮮度の反映
```

Phase 1 の完了条件として、この一巡を**最低1回、実データで通す**ことを要求する(§1.2)。

#### グラフ置換セマンティクス(追記しない)

出典を名前付きグラフ単位で持つ設計(§8.4)の最大の効用がここにある。**同一の(ソース × 対象)を再取得したときは、対応する名前付きグラフ全体を置き換える。既存グラフへの追記はしない。**

これにより、以下が特別な仕組みなしに正しく反映される。

| 更新の種類 | 置換による帰結 |
|---|---|
| 値の訂正(支出先法人名の誤りが直った) | 旧グラフが消えるため、古い値が残らない |
| 行の削除(前年度データから消えた事業) | 置換後のグラフに存在しないため、自動的に消える |
| ソース側の遡及改訂(RSの過年度分の restatement) | その年度のグラフを置き換えるだけで済む |

追記型にすると、上記いずれの場合も「消えたことを検出して削除する」処理が必要になり、そこが必ず腐る。置換型は再取得さえできれば常に正しい状態に収束する。

#### 撤回と履歴の扱い

- **廃止法令はKGから削除しない**。`repeal_status` を持つ版として残す(過去の事実は事実である)。イベント中心設計(§3)がこれを自然に表現する
- **改正は新しい時点版の追加**であり、旧版の書き換えではない
- 一方で、**ソースの誤りに由来する訂正は履歴として残さない**(グラフ置換で消える)。「政府が公表を訂正した」ことを記録するのは Phase 2 以降の課題として明示的に先送りする

#### KGのリリース版

**KG全体にバージョン(リリース)を持たせ、DCATでデータセットとして記述する。** 各リリースは「どのソースの、いつ取得分を含むか」を明示する(CQ10)。理由は、公共財として再現性を謳うなら「どの時点のKGに基づく分析か」を利用者が特定できなければならないため。

#### 更新失敗時の隔離

**更新の失敗が公開中のKGを壊さない構造にする。** 新しいリリースは別のデータセットにロードし、SHACL検証とCQテストを通過してから公開先を切り替える。検証に落ちた場合は前のリリースが残る。

#### 更新頻度と監視

| ソース | 頻度 |
|---|---|
| 法人番号(全件) | 月次 |
| e-Gov法令API | 月次(Phase 2で日次化を検討) |
| 予算書・RS | 年次(公表サイクルに追随) |

Phase 1 の頻度は日次を要求しないが、**スケジューラ前提の構造**(冪等な実行、前回取得との差分検出、失敗の記録と再実行)で作る。Phase 2 で日次ソース(調達・官報)が入っても構造を変えないため。

監視として、**ソースごとの最終成功取得日時をKGに保持し、想定頻度より古いソースを検知して報告する**。鮮度はアプリのエンティティページにも表示し、利用者が古いデータを古いと知れるようにする。

### 7.2 縦スライスの接続点

#### 実測で判明した制約(2026-08-22)

`https://laws.e-gov.go.jp/api/2/laws` の実レスポンスを確認した結果、**法令API v2 に所管省庁を示すフィールドは存在しない**。取得できるのは `law_info`(law_type, law_id, law_num, law_num_era/year/type/num, promulgation_date)と `revision_info`(law_title, law_title_kana, abbrev, category, amendment_*, repeal_status, repeal_date, remain_in_force, mission 等)であり、`mission` は "New" のような改正種別を表す値で所管とは無関係、`category` は事項別分類である。

したがって「法令の所管府省」は API から直接取れない。この制約を前提に、接続を2経路で設計する。

#### 経路1: 法令番号からの府省導出(決定的・完了条件の土台)

府省令・規則の法令番号には府省名が含まれる(例「令和七年厚生労働省令第十号」)。`law_num` と `law_num_type` から府省名を抽出し、府省コード/法人番号へ決定的に解決する。現行法令のうち法律は一部で、政令・府省令・規則が多数を占めるため、この経路だけで相当数の法令に所管が付く。

法律・政令(法令番号に府省名を含まない)はこの経路では所管が付かない。欠落として扱い、経路2で補う。

**旧省庁名の扱い(重要)**: 現行法令には2001年の中央省庁再編より前の省令が多数残る(大蔵省令・厚生省令・通商産業省令等)。これらは府省名の抽出には成功するが、現存する府省に解決できない。また複数府省を並記する共同省令もある。Phase 1 の規則を次のように定める。

- **現存する府省名に一致する場合のみ解決する**。共管(複数府省の並記)は府省ごとに複数のエッジを張る
- **旧省庁名は §8.2 の `UnresolvedReference` として保持し、件数を計測・報告する**(沈黙させない)
- **省庁再編の継承関係(旧省庁 → 現府省)のマッピングは Phase 2 に送る**。組織の履歴・同一性は §11.3 で Phase 2 の課題として先送りした問題であり、ここで簡易な対応表を作ると同じ問題を実装中に裏口から抱え込むため、意図的に扱わない

したがって §7.3 の検証項目3は「法令番号から府省名を抽出できる割合」ではなく「**現存府省に解決できる割合**」を測る。

#### 経路2: 根拠法令欄からの解決(精度目標)

行政事業レビューシートの様式には根拠法令欄があり、ここから法令への直結エッジを作る。解決は法令名(`law_title`)と**略称(`abbrev`)**での照合による。条・項レベルの解決は Phase 2 に送り、Phase 1 は法令単位までとする(これにより難度を大きく下げる)。

**未検証の前提**: RSシステムのCSVに根拠法令の列が含まれるかは実データで未確認(サイトがSPAのため静的取得では確認できず)。Phase 0 の先頭で実データを取得して検証し、結果で分岐する(§7.3)。

#### 接続点ごとの確度

```
法令(府省令・規則) ──[経路1: 法令番号]──→ 府省 ──所管──→ 予算事業 ──支出──→ 法人
法令(法律・政令)   ──[経路2: 根拠法令欄]──────────────────→ 予算事業
```

- **府省 → 事業**: RSのCSVに所管府省名があり、府省コード/法人番号へ決定的に解決。低リスク
- **事業 → 法人**: RSの支出先に法人番号がある行は決定的に接続。空欄・法人名のみの行が一定割合あることを前提とし、扱いを§8.2で定義
- **法令 → 府省**: 経路1で決定的(対象は府省令・規則)
- **法令 → 事業**: 経路2、解決率を計測

### 7.3 Phase 0 で先に検証すること

実装の順序として、以下を最初に実データで確認する。設計の前提が崩れた場合の分岐も定めておく。

| # | 検証項目 | 前提が崩れた場合 |
|---|---|---|
| 1 | RSのCSVに根拠法令の列があるか | 経路2を Phase 2 に送る。完了条件は経路1のみで達成できるため Phase 1 は継続 |
| 2 | RSのCSVに支出先の法人番号列があるか | 法人名のみでの名寄せに切り替え、解決率の目標を下げる。列自体が無ければ、支出先を Phase 2 に送り、完了条件を `法令 → 府省 → 事業` に短縮する |
| 3 | 法令番号から**現存府省に解決できる**法令の割合(旧省庁名を除いた実数) | 極端に低い場合(想定外)、完了条件を経路2ベースに切り替える |
| 4 | 府省コードと府省の法人番号の対応表が入手できるか | 府省コードのみを識別子とし、府省だけ `/id/gov/{府省コード}` を使う例外を認める(§4.1の統一方針を1点だけ緩める) |

いずれの分岐でも「縦スライス1本を完成させる」という Phase 1 の性格は変えない。短縮する場合も、短縮したことを完了報告に明記する。

## 8. エンティティ解決と品質の扱い

### 8.1 三段構成

1. **ID直結**: 法人番号・法令IDが与えられている場合はそのまま採用
2. **正規化**: 法人名は法人種別語の統一・旧字体・全半角・「株式会社」前後位置を正規化。**所在地はデジタル庁公式の `abr-geocoder`(アドレス・ベース・レジストリ準拠、活発にメンテされている)をローカルに組み込んで正規化する** — 住所正規化を自前実装しない
3. **blocking**: 正規化後の名称・所在地で候補を絞り込む
4. **判定**: 候補が一意なら採用。複数または0件なら**未解決として記録**

`abr-geocoder` を使う理由は、住所表記揺れの吸収が政府公式ツールで解決済みの問題であり、自前実装は品質でも保守でも劣るため。政府が「結合キーとその正規化ツール」までは提供しているという§1.4の認識を、実装で素直に活用する。

LLM 判定は Phase 1 では使わない(§7.1のソースは決定的解決の余地が大きく、LLM導入は評価コストに見合わない)。Phase 3 で非構造データが入る段で改めて導入を判断する。

### 8.2 未解決を「無かったこと」にしない

未解決の参照は、参照文字列を保持した `UnresolvedReference` として KG に残し、`解決済み/未解決` を API とアプリで区別して見せる。理由は、公共財として「政府データにこの曖昧さが存在する」こと自体が利用者にとって情報であり、沈黙させると出典に遡れないデータができるため。

**受け入れ基準に解決率を含める**: 支出先法人の解決率と根拠法令の解決率を計測し、パイプラインの出力として毎回記録する。目標値は最初の実測後に設定する(推測値を先に置かない)。

### 8.3 SHACL 検証ゲート

RDF生成の直後に SHACL 検証を通し、**不合格のグラフはストアにロードしない**。不合格分は隔離ディレクトリに出力し、違反内容を人が読める形で報告する。「一部が壊れていても入れてしまう」ことを許すと、公共財としての信頼性が最初に崩れるため、ここは厳格側に倒す。

> **追記(2026-08-23、決定43)**: **自オントロジーのクラスへの参照型制約(`sh:class`)は、
> グラフ単位のSHACLから外し、和集合レベルの参照整合ゲートで担保する。**
> 出典管理のため参照先エンティティの `rdf:type` は別の名前付きグラフにあり(例: 法令グラフの
> `law:jurisdiction` の参照先の型は法人番号グラフにある)、グラフ単位の検証では ABox が欠落して
> **正しいデータが原理的に不合格になる**(実測で確認)。これはグラフを跨いだ必須制約を
> SHACLから外してCQで担保した判断(決定・R2)と同じ類の問題であり、同じ扱いにする。
> 除去した (プロパティ, 期待クラス) の対応表は生成物として書き出し、リリース前の和集合検査が
> それを消費する(照合されない記録を作らない)。`sh:nodeKind sh:IRI` は維持する。
> なお ont_graph を渡して subClassOf を解決する案は、pySHACL が sh:targetClass も
> subClassOf* で評価するため**上位クラスのシェイプが多重適用され**、規模で検証コストが増える
> (実測: Ministry 1件に4シェイプ)。LinkML が ignoredProperties で偽violationを吸収するため
> 正しさは保たれるが、生成物が古いと吸収が外れる脆さもあり、採らない。

### 8.4 出典(provenance)

**名前付きグラフ単位で出典を持つ**方式を採る。各グラフに PROV-O で「どのソースの、いつ取得したファイルから、どのパーサバージョンで生成したか」を記録する。

要求v0.2ではRDF-starを挙げていたが、名前付きグラフ+PROV-Oを主方式に変更する。理由は (a) Fuseki と SPARQL 1.1 で確実に動く、(b) 出典の単位が「ソース×取得日」であり、トリプル単位の注釈は Phase 1 では過剰、(c) ツール互換性が高い。トリプル単位の注釈が必要になった箇所のみ RDF-star を後から足す。

## 9. APIと可視化アプリ

### 9.1 APIの責務

SPARQL を外に出さず、用途別のエンドポイントを提供する。

| 用途 | 返すもの |
|---|---|
| 検索 | 型混在のエンティティ候補(名称・型・要約) |
| エンティティ詳細 | 属性 + 関係の一覧(型別にグループ化)+ 各関係の出典 |
| 近傍サブグラフ | 指定ノードから深さ1-2のノード/エッジ(件数上限つき) |
| パス探索 | 2エンティティ間の経路(法令↔法人など) |

各応答は LinkML 生成の Pydantic モデルで型付けする。件数上限を必ず持ち、無制限のグラフ取得を許さない(hairball 防止をAPI側で保証する)。

### 9.2 アプリのUX

検索ボックス起点。エンティティページ(型別レイアウト)→ 近傍サブグラフ展開 → パス探索。全体グラフの一括表示は実装しない。全表示要素に一次資料へのリンクと取得日時を出す。想定ユーザーを特定類型に絞らない決定に従い、専門用語を避けた表示名を用い、専門機能(生データのダウンロード等)は副次的な位置に置く。

グラフ描画は Sigma.js。Phase 1 の規模では性能問題は出ないが、Phase 2 以降の拡大を見込んで最初から WebGL 系を選ぶ。

## 10. テスト戦略

TDD で進める。各層の性質に応じてテストの形を変える。

| 対象 | 方式 |
|---|---|
| パーサ(法令XML・予算XML・CSV) | ゴールデンファイル方式。実データの小片を固定入力として、期待する中間表現と比較 |
| エンティティ解決 | 正解ペアの固定セットに対する解決率・誤解決の計測。誤解決は解決漏れより重い扱い |
| オントロジー | LinkML スキーマから生成した SHACL で、正例・反例の両方を検証 |
| **URI整合性(最重要)** | **生成SHACLの `sh:targetClass` のIRI == 生成OWLのクラスIRI == サンプルインスタンスの `rdf:type` のIRI** を突き合わせる。LinkMLは `gen-owl --use-native-uris` の既定がTrue(自分の名前空間でクラスを宣言し外部語彙は `skos:exactMatch` でリンク)、`gen-shacl` は `class_uri` 側を使うため、**既定のままだとOWLは `jgkg:Event` を語りSHACLとデータは `prov:Activity` を語る乖離が起きる**。`gen-owl --no-use-native-uris` を明示し、このテストで固定する。CIで気づかないまま進むと全データの再生成になる |
| **オーバーレイ整合性** | §5.5 のオーバーレイTTLが言及するクラス・プロパティが、すべて生成OWLに存在することを検証(存在しない用語への公理はスキーマ未反映かタイポ)【→ **最終レビュー要修正8で反証** — `test_overlay_terms_all_exist_in_generated_owl`はTask 12で削除済み。現在のCIにこの検査は無い。`test_overlay_is_empty_pending_new_axioms`が「オーバーレイが空であること」だけを守り、用語存在検査そのものは復活していない】 |
| **コンピテンシー質問** | **CQ1〜CQ10 に対応するSPARQLクエリをテストとして持ち、期待結果と比較する。CQが増えたらテストが増える。オントロジー変更のリグレッション検知の主手段** |
| **更新の一巡** | **同一ソースの2世代分のスナップショットを固定入力として、グラフ置換で訂正・削除が正しく反映されることを検証。検証失敗時に前リリースが保持されることも検証** |
| RDF生成 | 生成トリプルのスナップショット比較 |
| API | 型検査 + 代表クエリの応答検証 |
| 縦スライス | **統合テスト: 固定の府省令から固定の法人まで、経路1でホップを辿って到達できることを自動検証**(§1.2の完了条件をテストとして表現する)。経路2は解決率の計測として別立て |
| フロント | コンポーネント単位 + 主要導線のE2E |

外部APIへの実アクセスはテストに含めない(記録した応答を用いる)。ネットワークに依存するテストは別枠の疎通確認として分離する。

## 11. 非機能要件・リスクと対処

### 11.1 非機能

- **再現性**: `docker-compose up` と1コマンドのパイプライン実行で、誰の環境でも同じKGが再構築できる。公共財として最重要
- **冪等性**: 同じ入力から何度実行しても同じ結果になる。中断からの再開が可能
- **観測性**: 各段の処理件数・失敗件数・解決率をパイプライン出力として記録する
- **規模**: Phase 1 は法人全件を入れても数千万トリプル規模。Fuseki の単一インスタンスで扱える

### 11.2 ライセンス対応

ソースごとの利用規約を機械可読メタデータとして KG に保持し、アプリ表示時に出典と規約を自動表示する。Phase 1 のソースはいずれも商用・再配布可(政府標準利用規約準拠、またはGIFコードリストのCC BY相当)だが、この仕組み自体を Phase 1 で作る(Phase 2 以降に制約付きソースが入るため、後付けにすると全面改修になる)。

公開ライセンスはコードとデータで分けて選定する(§13の残論点)。

### 11.3 リスクと対処

| リスク | 対処 |
|---|---|
| 法令APIに所管フィールドが無い(**実測で確定**) | 法令番号からの府省導出(経路1)を完了条件の土台に据える(§7.2) |
| 根拠法令欄の解決が難航、またはCSVに列が無い | 経路2は精度目標であり完了条件外。列が無ければ Phase 2 に送る(§7.3) |
| 支出先の法人番号が空欄 | 未解決として保持し、解決率を可視化(§8.2) |
| RSの事業IDが年度をまたいで変わる | Phase 1 は年度内で閉じる。年度またぎの同一性は Phase 2 の課題として明記 |
| 政府側のAPI仕様変更・廃止(RESAS APIの前例) | コネクタを薄く保ち、スナップショットを残すことで過去分の再処理を可能にする |
| ベースURIのドメイン未確定 | 設定1箇所に集約し、確定まで外部公開しない(§4.2) |
| 公共財としての持続性 | 再現性(11.1)を担保し、特定個人の運用に依存しない構成にする |
| **政府が横断統合データを外部提供する可能性** | ガバメントAI「源内」の政府共通データセット(官報79年分・法令・白書・国会会議録等)が外部提供されると前提が変わる。現在は閉域網・職員向けで外部利用不可。**監視対象とし、外部提供が始まった場合は本プロジェクトの価値を「オントロジー準拠の構造化と出典付きの関係」に絞り直す**(素材の入手性ではなく構造化が価値である、という現在の立場は変わらない) |
| **告示のベース・レジストリ提供(FY2026末目標)** | 提供されればPhase 2の官報・告示レイヤーが大幅に容易になる。逆に遅延した場合はPhase 2の当該部分を後ろに送る。Phase 1には影響しない |
| **サーバーレスコンテナ環境にトリプルストアを載せてしまう** | 永続ストレージがネットワークファイル共有しか無い環境(Azure Container Apps 等)にインデックスを置くと、mmapのコヒーレンシとロックの前提が崩れ、**複数レプリカがマウントした場合は静かなデータ破損になりうる**。§6.3の成果物方式(ステートフルなボリュームを使わない)で構造的に回避する |
| **インデックスが一時ディスク上限を超える** | サーバーレス環境の一時ディスクは小さい(Azure Container Apps は最大8 GiB)。数千万トリプルでは上限に近い。**Phase 1 で実サイズを実測し**、超える場合はブロックディスクを持つVM構成に倒す |
| **外向き通信量(egress)によるコスト超過** | 公開SPARQLはレスポンスサイズが予測できず、egressがVM代を超えうる。API層の件数上限・レート制限・CDNキャッシュを**コスト対策として**必ず入れる(§9.1) |
| **エンジン移行が外部利用者のクエリを壊す** | WMFはWDQSのバックエンド移行でクエリ書き換え支援のcontractorを雇っている。公共財としてエンドポイントを提供した後のエンジン変更は、破壊的変更のコストが利用者にも及ぶ。**規模の問題はエンドポイント分割で先に対処し(§6.2.3)、エンジン移行を最後の手段にする** |
| **TDB2のオンディスク形式がJenaバージョンに紐づく** | ビルド側と実行側でJenaバージョンがずれると成果物が読めなくなる恐れ。**manifestにバージョンを記録して実行側で照合する**(§6.3) |
