# Amazon Neptune の正体と OSS RDF ストア選定(2026-08-22)

> 問い: 「AWS Neptuneの裏側は何か。もしOSSのラッピングなら、その元のOSSを直接使う選択肢もあるのでは」
> 結論: Neptuneは既存OSSのラッパーではなく、「元のOSS」を使う筋は成立しない。ストアはFuseki (TDB2) を維持し、QLeverは条件付きの将来オプションに格下げする。

## 1. Amazon Neptune の正体

### 一次情報で確認できる事実

| 事実 | 出典 |
|---|---|
| AWSの公式表現は「**purpose-built** な高性能グラフDBエンジン」。OSS由来という記述はどこにもない | [AWS Neptune 製品ページ](https://aws.amazon.com/neptune/) |
| Neptuneの論文 "Amazon Neptune: Graph Data Management in the Cloud" (ISWC 2018) の著者に **Bryan B. Thompson** と **Michael Personick** が含まれる。両名はSYSTAP/Blazegraphのコア開発者 | [ISWC 2018 論文](https://ceur-ws.org/Vol-2180/paper-79.pdf) |
| Bryan Thompson (SYSTAP創業者・Chief Scientist) は現在AWSのSenior Principal Engineer | [LinkedIn](https://www.linkedin.com/in/bryanthompson2/) |
| Blazegraphの開発はNeptuneローンチ(2017年11月)前後で実質停止。最終安定版2.1.5は2019年3月19日 | [GitHub releases](https://github.com/blazegraph/database/releases) |
| AWSは「Blazegraph → Neptune 移行ガイド」を公式に用意している | [Migrating from Blazegraph](https://docs.aws.amazon.com/neptune/latest/userguide/migrating-from-blazegraph.html) |

### AWSが一度も言っていないこと

**「NeptuneのエンジンはBlazegraphをベースにしている」という趣旨の公式声明は、AWSのドキュメント・ブログ・論文のいずれにも存在しない。** 移行ガイドがあるのは「Blazegraphユーザーという移行元市場を認識している」ことを示すだけで、コードの系譜を示すものではない。ISWC論文もNeptuneのアーキテクチャを説明しているがBlazegraphを前身として言及していない。

検索で上位に出る「Neptuneは元々Blazegraphベース」と断言する技術ブログ類は、いずれもAWSの一次情報を引用しておらず、推測が伝播したものと考えられる。**根拠として扱うべきではない。**

### 妥当な推測の範囲

- **チームの移動は確定**(論文著者リストという一次情報で裏が取れる)
- **コードの系譜は不明**。人が移ったこととコードが移植されたことは別問題。ゼロから書き直した可能性も、一部を持ち込んだ可能性もどちらも否定できない
- **ストレージ層は確実にBlazegraph由来ではない**。cluster volume方式はBlazegraphの単一ノードjournalファイル方式とは根本的に別物

**したがって「元のOSSを直接使えばいい」という発想はNeptuneには成立しない。** Blazegraphを使ってもNeptuneの価値の大部分(分散ストレージ、自動修復、リードレプリカ)は得られない。

### ストレージ層

Neptune公式ドキュメントで確認できたこと:
- データは **cluster volume** という単一の仮想ボリューム(NVMe SSDベース)に格納される
- cluster volumeは **10 GB単位のsegment** の集合で構成される
- 各segmentのデータは**単一リージョン内の3 AZにレプリケート**される
- 最大128 TiB。segmentの破損を自動検出し他のコピーから自動修復する
- リードレプリカ追加時にデータのコピーは発生しない — 既存のcluster volumeに接続するだけ

出典: [Neptune Storage](https://docs.aws.amazon.com/neptune/latest/userguide/storage.html), [Storage, reliability and availability](https://docs.aws.amazon.com/neptune/latest/userguide/feature-overview-storage.html)

**訂正が必要な点**: 「6コピー(4/6書き込みクォーラム、3/6読み取りクォーラム)」という記述は **Neptuneのドキュメントには見つからなかった** — これはAuroraのドキュメントに書かれている設計である。AuroraとNeptuneが同一のストレージ実装を共有していることをAWSが明言した一次情報は確認できていない。設計思想が同系統であることは強く示唆されるが、「同じストレージ」と断定するのは踏み込みすぎ。

### Neptune Analytics は別物

Neptune AnalyticsはNeptune Databaseとは**別のエンジン**で、グラフをメモリ上に保持して大域的グラフアルゴリズム(PageRank、コミュニティ検出、ベクトル類似検索)を高速実行する分析用サービス。**openCypherのみ対応でSPARQLには対応していない。** RDFワークロードの選択肢にならない。

### NeptuneのSPARQL実装上の癖(公式ドキュメント記載)

AWSは自らSPARQL標準からの逸脱を文書化している([SPARQL standards compliance](https://docs.aws.amazon.com/neptune/latest/userguide/feature-sparql-compliance.html))。本プロジェクトに関係が深いもの:

1. **すべてのトリプルが名前付きグラフに属し、デフォルトグラフは全名前付きグラフのUNIONとして定義される。** グラフ指定なしでINSERT/LOADしたトリプルは `.../DefaultNamedGraph` というフォールバックグラフに入る
2. **`xsd:dateTime` は常にUTCに正規化され、タイムゾーン情報が破棄される。** 元のタイムゾーンは復元できない。**日本政府データのJSTタイムスタンプを扱う本プロジェクトでは実質的な情報損失になる。** Fuseki/TDB2ではこの問題は起きない
3. 数値リテラルは64bitまで。超えると例外
4. `=` / `!=` の意味論を仕様より拡張している。標準準拠のエンジンとは結果が変わりえる
5. 値域外リテラルは格納は受け付けるが数値として扱われず範囲フィルタが効かない
6. `DESCRIBE` はモードに関わらずデフォルトグラフのデータのみを使う

## 2. Blazegraph を採用すべきでない理由

**明確に不可。**

1. **リポジトリが2026年3月23日にアーカイブされ read-only になった。** blazegraph organization全体が管理者によってアーカイブ済み。「メンテナンスが停滞している」段階を通り過ぎ、**上流が正式に終了した**状態([github.com/blazegraph/database](https://github.com/blazegraph/database))
2. **最終安定版は2.1.5(2019年3月19日)。** 7年以上リリースがない
3. **セキュリティパッチの供給元が存在しない。** Java製で依存が多く、公共財として公開エンドポイントを運用する上で受容できないリスク。自前フォークでCVE対応する体力は個人〜小規模開発の前提と両立しない
4. **最大のユーザーであるWMF自身が離脱を決定した。** WDQSの評価文書は現状維持案を「2016年以降メンテナンスされていない」として却下している
5. **性能面でも劣る。** WMFの評価でロード速度は0.1M triples/秒未満で候補中最下位
6. **ライセンス**: GPL-2.0。SYSTAPが実質消滅しており商用ライセンスの取得先がないため**GPL-2.0単独として扱う必要がある**。Fuseki (Apache-2.0)、QLever/Oxigraph(寛容ライセンス)と比べて明確に不利

## 3. Wikidata (WDQS) の選択と教訓

### 何が起きたか

**QLeverが新バックエンドとして選定された。** WMFの公式文書: "QLever outperformed Blazegraph in all key indicators." 選定理由は予測可能な性能、GeoSPARQLを含む完全なSPARQL 1.1対応、モダンなアーキテクチャ、そして "QLever's thorough, publicly reviewable, and continuous integration testing" と開発者の応答性がOSSの原則に合致すること。

出典: [WDQS Backend Replacement](https://www.wikidata.org/wiki/Wikidata:SPARQL_query_service/WDQS_backend_update/Backend_Replacement)

**タイムライン**: 評価はFY26の10月〜3月。2026年4月にドキュメント作成とクエリ書き換え支援のcontractorを導入。**本番移行はFY27(2026年7月1日以降)から段階的に開始。** つまり2026年8月現在、**WDQSはまだBlazegraphで動いており移行は進行中**。

### 各候補の評価結果

| 候補 | 結果 | 理由 |
|---|---|---|
| **QLever** | **選定** | 全主要指標でBlazegraphを上回る。ロード1.7M triples/秒、インデックスサイズ最小、平均クエリ時間最短。CIテストの透明性と開発者の応答性を高評価 |
| **Virtuoso OSS** | 次点(唯一の真の競合) | 26年の実績で成熟しスケーラビリティ評価は最高だったが「運用フットプリントが重い、設定チューニングが複雑、結果のばらつきが大きい」。**OSS版が商用版と機能パリティにない** |
| **Apache Jena (Fuseki)** | 却下 | Wikidataのデータセットをロードできなかった(=100億トリプル超の話) |
| **Oxigraph** | 却下 | 同じくロードできなかった |
| **MilleniumDB** | 却下 | 必要な更新セマンティクスを欠く |
| **Blazegraph継続** | 却下 | 2016年以降メンテナンスされていない |

出典: [WDQS backend alternatives](https://www.wikidata.org/wiki/Wikidata:SPARQL_query_service/WDQS_backend_update/WDQS_backend_alternatives)

### graph split の顛末

**実施された。2025年5月9日**に本番投入され**2026年5月時点でも維持されている**。メイングラフ(query.wikidata.org)と学術論文グラフ(query-scholarly.wikidata.org)に分離。

重要なのはWMFの明言: **「学術グラフとメイングラフの再統合は計画されておらず、Blazegraph移行の一部でもない」**。graph splitは一時的な回避策ではなく**恒久的なアーキテクチャ決定**として残る。

出典: [WDQS graph split](https://www.wikidata.org/wiki/Wikidata:SPARQL_query_service/WDQS_graph_split)

### 本プロジェクトへの教訓

**教訓1(最重要): WMFのQLever採用を、名前付きグラフ必須のワークロードへの推薦と読んではいけない。**

WMFの評価表では名前付きグラフ(quads)対応について **Jena・RDF4J・Virtuosoが5/5、QLeverが0/5** だった。それでもQLeverが選ばれたのは **WDQSが名前付きグラフを実質的に必要としていないから**である。その証拠がgraph splitの実装方式で、これは1つのインデックス内の複数の名前付きグラフではなく**2つの独立したエンドポイント**として実現されている。

**本プロジェクトは名前付きグラフが必須要件。したがってWMFの判断を選定根拠に使えない。** ここを混同すると、後から「QLeverに移ったらGRAPH句を含むクエリが遅い」という形で問題が顕在化する。

**教訓2: 大規模データは「1つの巨大ストア」より「分割したエンドポイント」で解く方が現実的なことがある。**

WMFは世界最高レベルのRDF運用体力を持ちながら、最終的に「データを分割して別エンドポイントにする」という単純な解に落ち着き、それを恒久化した。本プロジェクトも将来データが数億トリプルを超えたとき、より強力なエンジンへの移行を検討する前に**「府省庁別・データセット別にエンドポイントを分ける」**選択肢を先に評価すべき。既存のFuseki + tar.gz成果物方式と極めて相性が良く(成果物を複数に分けるだけ)、エンジン移行より圧倒的に低コスト。

**教訓3: 評価プロセス自体が模範的。** 評価軸を事前に文書化し、複数候補を実データでロード・計測し、結果を公開し、コミュニティのフィードバックを取り込み、並行稼働のテストエンドポイントを経て段階移行する。将来QLeverを検討する際はこの手順をスケールダウンして踏むべき。特に「実データでロードできるか」を最初に確認する点 — JenaとOxigraphはこれで落ちた。

**教訓4: 移行には想像以上の付帯コストがかかる。** WMFはクエリ書き換え支援のためにcontractorを雇った。エンジンを変えるとエンジン固有の挙動に依存した既存クエリが壊れる。公共財として外部利用者にエンドポイントを提供する場合、**この破壊的変更のコストは自分だけでなく利用者にも及ぶ。** エンジン選定は「あとで変えればいい」で済まない決定。

## 5. 推奨

### 結論: Fuseki (TDB2) を維持。QLeverは条件付きの将来オプションに格下げ。

**Phase 1でFusekiを維持する理由**:

1. **名前付きグラフが必須要件で、TDB2はこの点で最も成熟している**(WMF評価5/5)。QLeverは2024年12月マージで上流自身が非効率を認めている。GRAPH句を多用するクエリで性能が読めないのは必須要件に対するリスクとして不釣り合い
2. **成果物配布方式との相性が最良。** Jena公式が「読み取り専用DBをコピーして複製しLBを前置する」構成を明示的に推奨している。**本プロジェクトが独自に発明した方式ではなく上流が想定・文書化した使い方**
3. **SHACL検証が同一スタック内で完結する。** QLeverにSHACL相当はない
4. **数千万トリプルはTDB2の射程内で天井には遠い。** 天井が問題になるのは数十億規模
5. **バス係数が構造的に高い。** Apache財団プロジェクトで複数コミッタ

**QLever移行のゲート条件**:
1. **自分の実データと実クエリで名前付きグラフを含むベンチマークを取る**(特に`GRAPH ?g { ... }`と複数グラフを跨ぐJOIN)
2. **WMFのFY27段階移行の結果を観察する。** 世界最大級のRDF運用による無料のbattle-testingを活用。ただしWDQSは名前付きグラフを使わないためquad関連の問題は露出しない点に注意
3. 月次バッチ更新方式なら**QLeverのUPDATE制約は問題にならない**(SPARQL UPDATEを使わない設計のため)。ここは相性が良い
4. 移行は「エンジン差し替え」ではなく**並行エンドポイント**で行う

**規模問題への対処順序(エンジン移行は最後の手段)**:
1. **成果物とエンドポイントを分割する**(府省庁別・データセット別)。Wikidataが恒久化した解。既存設計の延長で実現でき、リスクもクエリ破壊もない
2. **リードレプリカを増やす**(同じtar.gzをN台に展開してLB)。Jena公式推奨構成
3. **TDB2のチューニング**(JVMヒープを2-4GBに抑えOSページキャッシュを最大化)
4. **それでも足りなければQLever**(ゲートを通してから)

### Neptuneのアーキテクチャから学べること

「本方式はstorage/compute分離の簡易版か」への回答: **本質的にはyesだが、分離の粒度が決定的に違う。**

- Neptune: **ページ単位**で分離し分散ログで整合性を取る。書き込みが即座にdurableになり、リードレプリカは数ミリ秒の遅延で最新を見る。この機能のために分散ストレージ層という莫大な実装コストを払っている
- 本方式: **インデックス全体**の単位で分離し、月次の粒度で差し替える

**読み取り中心・月次バッチ更新という要件では、この粗い粒度がむしろ正解。** Neptuneが分散ストレージ層で解決している問題(書き込みのdurability、レプリカ間の一貫性)が本プロジェクトには存在しない。にもかかわらずNeptuneが得ている重要な便益は同じように得られる: computeのステートレス化、水平スケールの自明さ(同じ成果物をN台に展開)、障害復旧の単純さ。

**さらにNeptuneにはない利点も得られる**:
- **成果物をバージョン管理・ロールバックできる。** 前月のtar.gzを指定するだけで即座に巻き戻せる。Neptuneのスナップショット復元より圧倒的に軽量
- **CIで検証済みのインデックスだけが本番に出る**構造を強制できる

**設計上の具体的な示唆**:
1. **成果物をcontent-addressedにする**(ハッシュをファイル名やmanifestに含める)。Neptuneのsegment自動修復に相当する「壊れたデータを検出する」能力をチェックサムで安価に得る
2. **差し替えをアトミックにする。** symlink切り替えかblue/green。**TDB2はメモリマップを使うので稼働中のディレクトリを上書きしてはならない**
3. **ロールバックを明示的に設計する。** 過去N世代を保持し手順を文書化・自動化する。本方式の最大の強みなので暗黙にしない
4. **Jenaのバージョンをmanifestに記録し実行側で照合する。** TDB2のオンディスク形式はJenaバージョンに紐づくため(一次情報で確認した仕様ではなく予防措置としての提案)
