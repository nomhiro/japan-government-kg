# 日本政府ナレッジグラフ(Japan Government KG)要求詳細化ドラフト v0.1

- 日付: 2026-08-22
- ステータス: **レビュー待ちドラフト(承認前)**。本書は正式な設計書ではなく、調査に基づく要求のブラッシュアップ案+意思決定のための論点整理。
- 根拠資料: `docs/research/` 配下の3レポート(政府データソースカタログ / KG技術動向2024-2026 / 政府KG先行事例)

## 1. ビジョン(仮説)

日本国政府が公開する資料・データを、統一オントロジーに基づくナレッジグラフ(KG)として統合し、「政府情報の横断的なつながり」— 法令・組織・人・資金・政策文書・イベント — を誰でも検索・探索できるようにする。

構成は2層セット:

1. **データレイヤー**: 収集(コネクタ群)→ 正規化・抽出 → エンティティ解決 → オントロジー準拠KG
2. **可視化アプリ**: 検索起点でエンティティとその関係を探索できるWebアプリ

## 2. 設計原則(先行事例の教訓から導出)

先行事例調査(EU CELLAR、英legislation.gov.uk、米vocab.data.gov死亡、gBizINFO SPARQL廃止、統計LOD等)から、以下を本プロジェクトの不変原則とする:

1. **アプリファースト**: KGは内部表現とし、公開面は「KGでしか作れない体験」を持つアプリにする。SPARQL等の生エンドポイント公開はゴールにしない(するとしても後段)。利用者不在のエンドポイントは廃止レビューで死ぬ、が最大の教訓。
2. **識別子(URI/ID)設計に最優先投資**: 識別子と語彙はストアより長生きする(ELIの教訓)。URI体系は最初に固め、以後変えない。
3. **定常パイプラインの副産物としてKGを維持**: 日次で回り続ける収集・更新ジョブを最初から設計する(官報の90日無料期間がこれを強制する)。人手の熱意に依存する構成は禁止。
4. **政府の公式XML/APIを一次ソースにする**: 政府にRDF提供を期待しない。gBizINFOのSPARQL廃止・統計LODの停滞が示す通り、RDF/KG層は本プロジェクト側の付加価値領域(=空白地帯であり機会)。
5. **標準への準拠と外部ハブへのリンク**: GIF/IMIコア語彙・DCAT・ELI/Akoma Ntoso参考の法令モデル・Wikidata sameAs。将来の相互運用とSEOのため。
6. **全エッジに出典(provenance)**: どの一次資料のどのURLから、いつ、どの方法(決定的パース/LLM抽出)で得た関係かを必ず記録する。政府情報の信頼性を担保する製品価値そのもの。

## 3. スコープの段階化

「あらゆる資料」はv1では構築不可能(34ソース・3層のうちPDF非構造層は抽出コストが桁違い)。ドメインを絞ったPhase 1で価値実証し、共通基盤の上に増築する。

- **Phase 0(基盤)**: URI/ID設計、LinkMLスキーマ基盤、収集フレームワーク(コネクタ規約・生データレイク・日次スケジューラ)、コアエンティティ(府省・法人・地域)のマスター構築
- **Phase 1(1ドメインで価値実証)**: 下記候補AまたはBのいずれか1つ
- **Phase 2(接続の価値)**: もう一方のドメイン+人物・組織レイヤー(議員・幹部名簿・審議会委員)を追加し、ドメイン横断の接続を見せる
- **Phase 3(非構造層)**: PDF文書(白書・審議会・政治資金)のLLM抽出、GraphRAGによる自然言語質問

### Phase 1 候補A: 法令ライフサイクルKG

- チェーン: パブコメ → 閣議決定 → 国会審議(会議録API・議案) → 官報公布 → 法令本体(e-Gov法令API v2、時点管理・改正関係・委任関係) → 裁判例
- 強み: 法令API v2・会議録APIなど機械可読ソースが充実。「改正の歴史と審議の文脈を1画面で辿れる」体験はe-Gov法令検索に存在しない差別化。
- 想定ユーザー: 法務・渉外・政策担当、リーガルテック、研究者
- 弱み: 裁判例・パブコメはスクレイピング必要。法令間参照の解析(条文中の「〜法第○条」)は技術的挑戦。

### Phase 1 候補B: 資金フローKG(調査チームの推奨)

- チェーン: 予算書XML(財務省) → 行政事業レビューRSシステムCSV(事業・支出先法人番号) → 調達ポータル/官公需API → gBizINFO/EDINET(法人属性・資本関係)
- 強み: **全ソースが機械可読でLLM不要**、法人番号で決定的に連結できる。「国の予算がどの事業を通じてどの法人に流れたか」は社会的関心が高く、現在誰も統合していない。Phase 1として最速・最安・最も差別化が明確。
- 想定ユーザー: 報道・研究者・官公需営業・行政監視
- 弱み: RSシステムは2021年度以降のみ。年次データ中心で「日次更新の躍動感」は薄い。

推奨: **候補Bを推奨**(機械可読で完結し、KGの接続価値が最も見えやすいため)。ただし最終判断は想定ユーザー次第 → 未決事項1・2。

## 4. データソース(要約)

詳細は `docs/research/2026-08-22-government-data-sources.md`(34ソース、URL検証済み)。

- **①API層(16ソース)**: e-Gov法令API v2、e-Stat API、統計LOD(SPARQL)、国会会議録API、EDINET API v2、gBizINFO REST、法人番号Web-API、官公需API、ジャパンサーチSPARQL、NDLサーチ等
- **②バルク/スクレイピング層(10ソース)**: 予算書XML、RSシステムCSV、法人番号全件CSV、国土数値情報、衆参議員一覧、閣議決定、パブコメ等
- **③PDF非構造層(6ソース)**: 官報、白書、審議会資料、裁判例、政治資金収支報告書、幹部名簿

ライセンス上の要注意: 国土数値情報の非商用条件データ、官報の90日無料期間、政治資金収支報告書の掲載期間、裁判例サイトのスクレイピングポリシー、地理院タイルの測量法承認。

## 5. オントロジー・ID設計方針

### 5.1 IDバックボーン(名寄せの一級市民)

| エンティティ | 正準ID | ソース |
|---|---|---|
| 法人・団体 | 法人番号 | 国税庁法人番号公表サイト(全件月次) |
| 法令 | e-Gov法令ID / 法令番号 | e-Gov法令API v2 |
| 地域 | 全国地方公共団体コード・統計LOD地域URI | 総務省/統計LOD |
| 住所 | アドレス・ベース・レジストリ町字ID | デジタル庁 |
| 人物 | 正準IDなし → 自前ID + Wikidata sameAs | 議員・幹部名簿から構築 |

### 5.2 URI設計(Phase 0で確定、以後不変)

- 形式: `https://{domain}/id/{type}/{正準ID}`(例: `/id/law/{法令ID}`、`/id/org/{法人番号}`)
- W3C GLDベストプラクティス準拠(技術非依存・コンテンツニュートラル)
- 外部リンク: Wikidata(法令P8610・議員・省庁)、統計LOD、ジャパンサーチへsameAs

### 5.3 スキーマ管理

- **LinkMLをソース・オブ・トゥルース**とし、Gitで管理。CIでOWL/SHACL(RDF用)とJSON Schema/Pydantic(アプリ・LLM抽出用)を同一定義から生成
- 参照語彙: GIF/IMIコア語彙(人・組織・場所・イベント。参照するがフォークし、IMIの存廃に依存しない)、DCAT(データセットメタデータ)、ELI/Akoma Ntoso(法令構造の参考)、SKOS(用語集)
- オントロジーの拡張はドメイン追加ごとにLinkMLモジュールを追加する方式

## 6. アーキテクチャ方針(2案+推奨)

### データパイプライン(両案共通)

```
コネクタ群(ソース別、日次スケジュール)
  → 生データレイク(取得時点のスナップショット保全。官報90日対策・再処理可能性)
  → 正規化・抽出
      構造化ソース: 決定的パーサ(LLM不使用)
      PDF/HTML非構造: LLM抽出(LinkML由来Pydanticスキーマ+BAML/Instructor)→ スキーマ検証 → 人手レビューキュー
  → エンティティ解決(ID直結 → 文字列blocking → LLM判定の三段)
  → KGロード(provenance付き)
  → クエリAPI層 → 可視化アプリ
```

### 案A: RDF中心(LOD公開・長期公共財重視)

GraphDB/Fuseki(+公開時QLever)、SHACL検証、RDF-starで出典注釈。標準準拠・外部連携が最強だが、開発人材が薄くアプリ開発速度で不利。

### 案B: プロパティグラフ中心(アプリ提供速度重視)

Neo4j(Cypher 25=ISO GQL準拠)、エッジプロパティで出典注釈、GraphRAG/可視化エコシステムが厚い。外部LOD連携は弱く、後からのRDF化にマッピング工数。

### 推奨: 案B開始 + LinkMLで案A移行余地を確保

- 設計原則1(アプリファースト)に従い、Phase 1は案Bで最速に価値実証
- LinkMLスキーマとURI/ID設計(5章)を先行確定しておけば、RDFエクスポートは後からLinkMLマッピングで生成可能(後悔しない打ち手)
- 「二次公共財としてのLOD公開」を目的に含める判断になった場合のみ案A(または折衷: 正式KG=RDF管理+可視化用LPG投影)へ — 未決事項4
- AWS前提が確定している場合はNeptune(RDF+openCypher両対応)も選択肢

## 7. 可視化アプリ要求(ドラフト)

- **検索起点UX**(全体グラフの毛玉表示は禁止): 検索ボックス → エンティティページ → 近傍サブグラフ展開 → パス探索
- エンティティページ: 法令/法人/議員/府省/事業ごとに型別レイアウト+関係一覧+出典リンク
- グラフビュー: Sigma.js(WebGL、10万ノード級)第一候補。パス探索・時点スライダー(法令改正履歴)等
- 全表示要素に出典(一次資料URL)を明示 — 政府情報の信頼性がプロダクト価値
- 自然言語質問(GraphRAG層)はPhase 3。正式KGを入力として再利用し、検索用グラフと正式KGを混同しない

## 8. 非機能要件・リスク(ドラフト)

- **更新性**: 日次パイプライン(官報・調達・パブコメ)、月次(法人番号全件)、年次(予算・RS)。失敗検知と再実行
- **provenance**: 全エッジに出典URL・取得日時・抽出方法を保持
- **時点管理**: 法令は時点指定(law API v2)、組織は改編履歴、人物は在職期間 — 「いつの時点で真か」をモデルに含める
- **ライセンス**: ソースごとの利用規約を機械可読メタデータとして管理し、アプリ表示時に出典・規約を自動表示。非商用条件ソースは商用判断が出るまで組み込まない
- **LLM抽出コスト**: PDF層は別予算として見積り(Phase 3まで先送り可)
- **リスク**: スクレイピング先のサイト改修(会議録・議員一覧等)、APIの仕様変更・廃止(RESAS APIの前例)、政治資金等センシティブ領域の取り扱い方針

## 9. 未決事項(ユーザー判断が必要な論点)

1. **目的の性格**: 商用プロダクト / 社内・個人活用 / 公共財(OSS・LOD)のどれか? → ライセンス対応(非商用ソースの扱い)とアーキテクチャ(案A/B)に直結
2. **Phase 1のドメイン**: 候補A(法令ライフサイクル)か候補B(資金フロー)か? 調査に基づく推奨はB
3. **想定ユーザーと課題**: 誰の・どの課題を最初に解くか(法務 / 報道・研究 / 官公需営業 / 一般市民)
4. **LOD/SPARQL公開をゴールに含めるか**: 含めるなら案A(RDF)寄りに倒す必要
5. **インフラ前提**: クラウド(AWS等)指定の有無、運用予算規模
6. **LLM利用方針**: 抽出に使うモデル・予算、人手レビューの体制
7. **政治資金・人事など人物データの取り扱い方針**: 公開情報とはいえ、可視化の倫理・炎上リスクの線引き
8. **リポジトリ・開発体制**: 個人開発か、チーム化前提か(パイプライン監視の当番設計に影響)
